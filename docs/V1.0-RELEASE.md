# RaceLab V1.0 — packaged Windows release

This document covers everything that is true of RaceLab as an **installed
Windows application** rather than as a development checkout: how the installer
is produced, where an installed build stores things, what Windows does about the
network, and the acceptance procedures that have to be run by hand before the
version is moved.

**The application version is 1.0.0.** That bump was a deliberate release
decision taken after all three manual acceptance runs passed — packaged-build
FH6 (section 7), fatal startup error (section 4a) and clean-profile
installation (section 6). `tests/release-config.test.mjs` pins the version in
all four places that declare it, including the label in the window, and fails
on purpose if any of them is changed without that decision being made again.

---

## 1. Producing the build

```bash
pnpm install
pnpm tauri build
```

Two artifacts are produced:

| Artifact | Path |
| --- | --- |
| Application executable | `src-tauri/target/release/racelab.exe` |
| Windows installer | `src-tauri/target/release/bundle/nsis/RaceLab_<version>_x64-setup.exe` |

The installer bundling step downloads the NSIS toolchain from GitHub the first
time it runs. That download is the only part of the build that needs network
access, and a reset connection fails the bundle step while leaving the compiled
`racelab.exe` intact — re-running `pnpm tauri build` resumes from there.

### What the packaging configuration guarantees

- **Release profile**, optimized, x86-64.
- **No console window.** `main.rs` carries
  `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`, so the
  packaged executable is a GUI-subsystem binary. Debug builds keep their console
  so `pnpm tauri dev` can still print.
- **Per-user install, no administrator rights.** The NSIS installer runs in
  `currentUser` mode and installs under the user's own profile. Nothing in
  RaceLab needs elevation, at install time or at run time.
- **No developer toolchain at run time.** The frontend is compiled by
  `pnpm build` and embedded in the executable. An installed build has no
  dependency on Node, pnpm, Rust, Cargo or a source checkout, and never contacts
  a development server. (`tauri.conf.json`'s `devUrl` string is embedded as
  inert configuration metadata; the release build serves only its embedded
  assets. `pnpm tauri dev` is the only thing that reads it.)
- **No updater.** `createUpdaterArtifacts` is false; there is no update server
  and RaceLab does not phone home.
- **WebView2** is installed through Microsoft's bootstrapper if it is missing.
  It is already present on Windows 11 and on up-to-date Windows 10.

## 2. Where an installed build stores things

Everything derives from Tauri's resolved application data directory, which is
read exactly once in `lib.rs`. Nothing in RaceLab resolves a path from the
process's current working directory, and
`tests/release-config.test.mjs` enforces both facts.

```
%LOCALAPPDATA%\com.tahagurvardar.racelab\
├─ sessions\<session-id>\manifest.json, frames.rlframes, analysis.json
├─ captures\<unix-ms>-<id>.rlcap          (Diagnostics only, opt-in per capture)
├─ logs\racelab.log, racelab.previous.log
└─ settings.json
```

`settings.json` is written only when there is something to record — a changed
storage budget, or the first time FH6 telemetry is decoded. A fresh
installation that has never seen the game has no settings file, and that is not
an error.

## 3. Windows network behaviour and the firewall

**RaceLab requires no firewall exception and triggers no firewall prompt.**

The telemetry socket binds `127.0.0.1` (see `ingress::LISTEN_ADDRESS`). Loopback
traffic is exempt from Windows Defender Firewall filtering, so a loopback-only
listener is never the subject of a prompt and needs no rule.

This was **not** true through V0.10, which bound `0.0.0.0`. A wildcard bind
accepts datagrams on every interface, and Windows prompts the user the first
time such a socket is opened. Running a V0.10-configured release build on this
development machine created exactly that rule:

```
Program   : ...\target\release\racelab.exe
Name      : RaceLab
Direction : Inbound   Action : Allow   Profile : Public
```

Binding loopback removes the cause rather than the symptom, and is the minimum
permission the product can operate with.

**The cost, stated plainly:** RaceLab now receives telemetry only from a game
running on the same PC. FH6 Data Out pointed at `127.0.0.1:20440` on the same
Windows machine is the supported configuration. Telemetry sent from an Xbox, or
from a second PC on the same network, is no longer received.

`production.rs::the_telemetry_socket_is_bound_to_loopback_and_nothing_else`
pins this: it asserts the constant, proves the wildcard address is still free
while the listener is running, and proves loopback datagrams still arrive.

### Stale rules on this development machine

Firewall rules created by earlier `0.0.0.0` builds still exist for both the
debug and release executables, and for several test binaries. They are now
unnecessary. Removing them is a change to system security settings, so it has
been left to you rather than done automatically:

```powershell
Get-NetFirewallApplicationFilter |
  Where-Object { $_.Program -like '*racelab*' } |
  Get-NetFirewallRule |
  Remove-NetFirewallRule -WhatIf
```

Drop `-WhatIf` once the listed rules look right. They will not be recreated.

## 4. Logging

One active file and one previous file, each capped at 1 MiB, so the log
footprint can never exceed 2 MiB whatever happens.

What is logged: startup with version and data directory, the resolved storage
budget, the bound UDP port, first FH6 detection, settings changes, shutdown, and
failures — listener, capture, recorder, recovery, analysis and any Rust panic,
including panics on background threads.

What is never logged: telemetry frames, packet bytes, capture contents, or
anything describing what was driven. Session identifiers and file paths are
recorded because a support reader needs them to find a session; nothing about
the driving is. The logging API deliberately offers no way to log a frame.

A logging failure is never a product failure: every disk operation in
`logging.rs` discards its error, and a log directory that cannot be created
simply means nothing is written.

## 4a. Fatal startup errors

A GUI-subsystem build has no console, so a failure *before the window exists*
had nowhere to go. Through the first V1.0 pass, a fatal configuration error —
an unusable data directory, a sessions root that cannot be created, a malformed
`RACELAB_STORAGE_BUDGET_BYTES` — made RaceLab exit silently: the user
double-clicked it and no window ever appeared, which is indistinguishable from
the application not being installed.

**Root cause.** Tauri's `build()` does not return a setup-hook error; it
**panics** internally (`tauri-2.11.5/src/app.rs:1425`). The `Err` arm around
`build()` was therefore never reached, and the panic — logged by the panic hook,
but printed to nobody — was all that happened. Exit code was 101.

**Fix.** Everything fallible in `setup` now lives in `configure()`, which
returns `Result<(), String>`. The closure reports a failure itself rather than
handing it back:

```rust
.setup(|app| {
    if let Err(error) = configure(app) {
        startup_error::report(&error);
    }
    Ok(())
})
```

`startup_error::report` logs the original technical error in full, shows one
native `MessageBoxW` from `user32`, and exits **1**. It never returns. The
`Err` arm around `build()` routes through the same function, for failures that
do come back rather than panicking.

**No new dependency.** `user32` is already linked by every Windows GUI binary.
A dialog plugin could not have helped here anyway: this has to work at the exact
moment the application failed to build, when no plugin, window or event loop
exists to route a dialog through.

**Scope.** This is only for failures before the normal UI can start. Nothing
else in RaceLab calls it, and a test asserts that `startup_error::report`
appears exactly once in `lib.rs` and nowhere else. Background and runtime
failures keep using the connection, recorder, analysis and storage states they
already have; a modal that could appear while the application is running would
be a worse failure than the one this fixes.

What the user sees, verbatim, for the documented test seam:

```
RaceLab could not start.

RACELAB_STORAGE_BUDGET_BYTES must be a whole number of bytes

Your recordings have not been changed.

Technical details are in:
%LOCALAPPDATA%\com.tahagurvardar.racelab\logs\racelab.log
```

One OK button, labelled by Windows in the user's own language. The reason is
flattened to a single line, whitespace-collapsed and capped at 300 characters,
so no backtrace or `Debug` dump can reach it; the log keeps the original in
full. The log line is named only when logging actually opened a file.

### Manual startup-error acceptance

```powershell
$env:RACELAB_STORAGE_BUDGET_BYTES = "not-a-number"
& "$env:LOCALAPPDATA\Programs\RaceLab\RaceLab.exe"
```

The dialog must appear. Acknowledge it, then confirm the failure was honest and
that the reason was recorded:

```powershell
$LASTEXITCODE
Get-Content "$env:LOCALAPPDATA\com.tahagurvardar.racelab\logs\racelab.log" -Tail 2
```

`$LASTEXITCODE` must be `1`, and the log must hold
`ERROR RaceLab could not start: RACELAB_STORAGE_BUDGET_BYTES must be a whole number of bytes`.

Restore normal operation and confirm it:

```powershell
Remove-Item Env:RACELAB_STORAGE_BUDGET_BYTES
& "$env:LOCALAPPDATA\Programs\RaceLab\RaceLab.exe"
```

RaceLab must start normally. No session is created, modified or deleted by any
step above: the failure happens before anything is written.

## 5. Settings

One setting: the **storage budget**, in the Sessions view.

Precedence is environment → settings file → built-in default (8 GB). The
`RACELAB_STORAGE_BUDGET_BYTES` variable still wins and an unparseable value is
still a startup error, exactly as in V0.10, so every V0.10 retention test and
validation document remains valid. When the environment sets the budget, the UI
says so and refuses to change it.

A new budget takes effect at the **next launch**. The retention worker is given
its policy once at startup, and leaving that V0.10 contract untouched was worth
more than applying a budget change live. Nothing is deleted at the moment the
setting changes.

## 6. Clean-profile acceptance

**Status: PASSED on a fresh standard Windows user account.**

A fresh *standard* (non-administrator) profile is the strongest clean
environment available without a second physical machine, and it is what the
V1.0 gate was closed on.

### What this run proves

1. **No administrator rights are needed, for real.** A standard user account
   cannot elevate silently. The installer ran and RaceLab launched under it, so
   the `currentUser` NSIS mode is doing what it claims rather than being
   masked by an administrator profile.
2. **No developer toolchain is required.** Rust and pnpm install onto the
   *user* `PATH` (`%USERPROFILE%\.cargo\bin` and the pnpm home), not the
   machine `PATH`, so they are genuinely absent from a fresh profile. A hidden
   dependency on `cargo` or `pnpm` would have failed here.
3. **Per-user storage is correct and isolated.** A fresh profile has an empty
   `%LOCALAPPDATA%\com.tahagurvardar.racelab\`, so first-run state, settings,
   logging and the sessions root were all exercised from nothing — and the
   development profile's recordings were neither read nor touched.
4. **First run is genuinely first run.** The first-run panel appeared for a
   user who had never seen it, which is the only way to test it honestly once
   the development profile has recorded its marker.
5. **Start-menu registration and launch work per user.**

### What it still does not prove

Stated plainly rather than folded into the pass:

- **WebView2 genuinely absent.** WebView2 is installed machine-wide, so a fresh
  profile still has it. The bootstrapper path remains unexercised.
- **Absence of a firewall prompt is not newly proven here.** Windows Firewall
  rules are machine-scoped, so the allow-rules left behind by earlier `0.0.0.0`
  builds still applied under the new profile. The loopback bind is proven by
  test and by `Get-NetUDPEndpoint` (section 3), which is the real evidence;
  this run does not add to it.
- **A machine with no Rust/Node/pnpm installed at all.** Anything on the
  *system* `PATH` is still visible to a fresh profile. Point 2 above covers the
  user-`PATH` tools, which is where these three actually live, but a
  system-wide install of one of them would not have been caught.

These three are accepted deliberately for 1.0.0. None of them is a defect in
RaceLab; each is a limit of the environment the test ran in, and the full
clean-machine procedure below remains the way to close them.

### Procedure, for a genuinely clean machine

1. Copy `RaceLab_1.0.0_x64-setup.exe` to the clean machine. Copy nothing else.
2. Confirm the machine has no Rust, Node or pnpm: `where cargo`, `where node`,
   `where pnpm` should all fail.
3. Run the installer. Confirm it does **not** prompt for administrator rights.
4. Launch RaceLab from the Start menu.
   - Confirm no console window appears.
   - Confirm **no Windows Firewall prompt appears.**
   - Confirm the first-run panel is shown, naming `127.0.0.1` and `20440`.
5. Follow the first-run instructions in FH6 and drive.
6. Confirm the first-run panel reports success, then continue past it.
7. Complete a session, then confirm it appears in Sessions with an analysis.
8. Close and reopen RaceLab. Confirm the first-run panel does **not** return.
9. Reopen the historical session and confirm its analysis still reads.
10. Uninstall from Settings → Apps. Confirm the program directory is removed.
11. Confirm `%LOCALAPPDATA%\com.tahagurvardar.racelab\` still holds the
    recordings — uninstalling the application must not delete a user's driving
    data. Delete it by hand if that is what you want.

## 7. Packaged-build manual FH6 acceptance

**Status: PASSED on the real installed build.** Observed: normal launch, no
console window, no elevation, no Windows Firewall prompt, correct first-run
instructions, FH6 connected on `127.0.0.1:20440`, live telemetry, automatic
recording, correct session completion, analysis completed and became available
in **788 ms**, and the historical Sessions UI remained functional.

The table below is retained as the repeatable procedure for future builds.

Run the installed `RaceLab.exe`, not `src-tauri/target/release/racelab.exe`
directly, so the acceptance covers the installed layout too.

### Before starting

```powershell
Remove-Item "$env:LOCALAPPDATA\com.tahagurvardar.racelab\settings.json" -ErrorAction SilentlyContinue
Remove-Item "$env:LOCALAPPDATA\com.tahagurvardar.racelab\logs" -Recurse -ErrorAction SilentlyContinue
```

Deleting `settings.json` restores the first-run state. It does **not** delete
recordings.

| # | Step | What must be true |
| --- | --- | --- |
| 1 | Launch RaceLab with FH6 closed | Window appears in about a second. No console window. First-run panel shows, naming `127.0.0.1` and port `20440`. Status bar reads "No game detected" / "Waiting for game". Nothing looks broken. |
| 2 | Leave it sitting for a minute | Detection line still reads "Listening on 127.0.0.1:20440. Nothing has arrived yet…". No error, no spinner, no stuck state. |
| 3 | Start FH6, leave Data Out **off**, reach the main menu | Still "waiting for game". RaceLab must not claim a connection. |
| 4 | Set Data Out ON, address `127.0.0.1`, port `20440` | Within a few seconds of driving, the first-run panel flips to "Forza Horizon 6 connected". |
| 5 | Press Continue, then drive for two minutes | Overview shows live speed/RPM/inputs. Status bar: Connected, Good, Session active, Recording. |
| 6 | Pause into a menu for ~15 s, then resume | Status goes to "Telemetry paused" with a countdown; the session is **held**, not ended. Resuming continues the same session. |
| 7 | Pause for longer than the grace period | The session completes. A new drive starts a **new** session. |
| 8 | Open Sessions | The finished session is listed with a duration and frame count, and an analysis appears without anyone asking for one. |
| 9 | Open the session's analysis | Turns, driving events and slip episodes read. No value is shown as `0` where it means "unavailable". |
| 10 | Close FH6 while RaceLab is open | The session completes cleanly. RaceLab returns to "waiting for game" rather than erroring. |
| 11 | Close RaceLab, reopen it | First-run panel does **not** return. Historical sessions still list and open. |
| 12 | Launch RaceLab **before** FH6, then start FH6 and drive | Telemetry is picked up automatically with no interaction. |
| 13 | Launch FH6 **before** RaceLab, drive, then start RaceLab | Telemetry is picked up automatically with no interaction. |
| 14 | Check the Sessions view storage line | Used bytes and the budget read sensibly. Changing the budget saves and says it applies next launch. |
| 15 | Check `%LOCALAPPDATA%\com.tahagurvardar.racelab\logs\racelab.log` | Startup, bound port, first detection and shutdown lines are present. No telemetry values anywhere in the file. |
| 16 | Check Task Manager while driving | RaceLab's own CPU stays low and memory stays flat over a long session. |

### Low-disk behaviour

Worth exercising once, on a spare volume or with the disk deliberately close to
full, because it is the one failure this product has actually hit:

- While recording, fill the disk. The recording must fail **visibly**: the
  status bar shows "Recording failed" with the reason, and the session's
  manifest finalizes as incomplete rather than claiming success.
- RaceLab must not hang, spin or deadlock, and the UDP listener must keep
  running.
- Freeing space and driving again must produce a normal session.

## 8. Known limitations carried forward, unchanged

These are unresolved and are **not** resolved by guessing. None of them breaks
existing truthful behaviour, so none blocks V1.0.

1. Slip-threshold portability across vehicles is not established.
2. Gear codes `1` and `11` remain unestablished; the raw code is shown in
   Diagnostics and never rendered as a gear.
3. Lap and event telemetry remain insufficiently validated.
4. The boost unit remains unestablished.

## 9. Gate for moving to 1.0.0

**All five are met. The version was moved to 1.0.0 on that basis.**

- [x] Code gate: `cargo test`, the frontend suite, `tsc --noEmit`, Clippy
      `-D warnings` and both formatters all pass.
- [x] A packaged build is produced and runs.
- [x] Packaged-build manual FH6 acceptance (section 7) passes.
- [x] A fatal startup error is visible to the user (section 4a).
- [x] Clean-profile installation (section 6) passes, with its three residual
      gaps accepted deliberately and recorded there.

The version is declared in four places and they must move together:
`package.json`, `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json` and the
label in `src/components/AppShell.tsx`. `src-tauri/Cargo.lock` follows from
`Cargo.toml` on the next build. `tests/release-config.test.mjs` asserts all
four agree and separately pins the expected value, so the next bump has to be
made on purpose.
