# V0.5.1 — Telemetry classification cleanup

2026-09-19. This patch separates packet classification from protocol identification and replaces the generic Rejected packets UI with four counters. The user-reported completed manual V0.5 validation is recorded in [V0.5-VALIDATION.md](V0.5-VALIDATION.md). No frozen UDP ingress, capture format, session persistence, product feature or visual redesign changes are included.

## Classification contract

Each packet processed while listening increments exactly one counter:

| Snapshot field | Meaning |
|---|---|
| `valid_active_fh6` | Active FH6-layout packet passing decoding, physical checks and applicable live timestamp checks; includes successful probe packets before lock |
| `valid_inactive_fh6` | Inactive FH6-layout packet passing structural/finite-value checks; active-driving physics are unavailable and not applied |
| `invalid_fh6` | Packet from the locked FH6 endpoint failing size, decode, finite-value, control, active-physics or active-clock validation |
| `unknown_protocol` | Unrecognized traffic before lock, or traffic from a different endpoint while locked |

Classification alone does not authenticate the game. In particular, a zero-filled 324-byte packet satisfies the inactive layout but cannot establish a protocol lock. Inactive packets lacking plausible raw engine/motion or progressing probe clocks count as valid inactive without publishing canonical frames, creating sessions, or increasing lock confidence. Multiple consecutive invariant-valid frames and progressing timestamps remain required for identification. Failed active probes remain unknown until a stream is identified; they are not counted as confirmed invalid FH6.

Counters reset on listener restart and survive stop/disconnect for inspection. They do not reset on automatic session changes. The four-way sum equals packets processed in that listener run. Legacy `invalid_packets` remains an alias for `invalid_fh6`; legacy `valid_packets` and `valid_frame_hz` continue to count frames actually published after lock, including both active and inactive frames. Consequently, successful probes count in the classification counters but not published-frame totals/rate. Raw capture still receives every packet independently of classification.

## Menu/loading cleanup

The earlier detector conflated insufficient inactive probe evidence with malformed packets. It also applied live clock continuity rules across inactive menu/loading data. Both paths could feed the generic rejected counter. The user's observation identifies the affected game states; no additional private menu packet samples were supplied with this request, so exact offending byte sequences were not independently reproduced from a new live capture.

V0.5.1 decodes packet validity separately from the extra evidence used to lock the protocol. Once locked, valid inactive packets keep the connection fresh, publish nullable inactive telemetry, and enter/maintain session grace. They do not reduce confidence or produce invalid-packet health degradation. Inactive clock values are retained in raw/source-specific data but do not have to satisfy active-driving continuity. An inactive packet clears the active live-clock baseline; the first returning active packet establishes a new baseline and subsequent active packets must again pass regression/jump/stall checks.

This does not label arbitrary timestamp jumps as understood resets. Offline timestamp validation is unchanged and remains stricter across recorded inactive intervals. Non-finite implemented floats, invalid activity flags and steering -128 are still invalid from a locked source, even in menus. Packet size alone is never proof of FH6 identity.

Unknown traffic has its own counter and does not change locked confidence or clear/replace the latest FH6 validation result. Thus unrelated packets neither hide good live values nor resurrect an old frame after an actual FH6 validation failure. Missing valid frames still trigger the existing silence/grace/disconnect behavior. No grace deadline, session ID or transport lifecycle rules changed.

## Regression coverage

Three added Rust integration tests cover:

1. Inactive zero packets and discontinuous inactive probe timestamps: valid inactive counters, no rejected count, no issues, no lock/session/hub publication without sufficient evidence, followed by normal active identification.
2. Menu/loading zero values with repeated timestamp regressions/large jumps after lock: no invalid count, 100% confidence, GOOD health, null canonical dynamics, same-ID short grace recovery, and fixed grace expiry.
3. Unknown traffic versus malformed FH6: unknown pre-lock/random-layout/foreign traffic, unchanged locked confidence, non-finite inactive values, steering -128, wrong size, invalid active physics, independent raw capture counts, exact counter sum, preservation of last FH6 issues, and counter reset on restart.

The existing raw-capture independence test now checks that foreign traffic preserves the latest inactive FH6 values and increments unknown rather than invalid. Existing timestamp, detector, normalization, session, bounded-hub and frontend tests remain part of the full suite.
