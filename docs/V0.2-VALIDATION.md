# RaceLab V0.2.1 hardening validation — 2026-09-18

## Freeze decision

**Do not freeze V0.2.1 as reliable ingress yet.** The requested code hardening is implemented, but the sequence-verified matrix failed five of ten cases. Across 10,000 successfully submitted synthetic datagrams, ingress and the test observer both recorded 9880; **120 sequence values were missing**. The current 4 MiB configuration lost packets in all three 10 Hz runs. The final 4 MiB run also missed seq=1000. These failures are preserved, not weakened into passing thresholds.

Claude's V0.2 review was not present in the repository or the local review-file search. CLAUDE.md contains review-role instructions, not the review. Its location/text was requested during the task but was not supplied. This pass follows the user's explicit hardening requirements; it does not claim to have verified the missing review.

## Before / after

| Concern | V0.2 behavior | V0.2.1 behavior |
| --- | --- | --- |
| Packet consumers | No consumer API; future adapters would need ingress edits | Borrowed CapturedPacket and PacketSink trait; inject a consumer at Listener construction without modifying the receive loop |
| Ingestion timing | Wall-clock packet timestamp; monotonic clock used only for rate sampling | Session-relative monotonic microseconds captured immediately after recv_from, before statistics lock/callback; wall time retained for display/logging |
| Synthetic loss evidence | Packet/byte totals only | Test-only sink collects sequence observations, exact gaps/duplicates/unexpected/malformed values, final tail, and timestamp ordering |
| Buffer experiments | Fixed 4 MiB request; one earlier default-buffer failure | Public game-agnostic buffer option supports untouched SystemDefault and Requested(bytes); repeated controlled comparisons |
| Buffer description | Wording implied allocated OS capacity | Winsock accepted/read-back SO_RCVBUF value; no allocation or queue-capacity guarantee |
| Frontend recovery | Failed initial get_telemetry_stats left controls disconnected despite later events | Any successful stats event restores connected state and clears connection errors; late initial-query rejection cannot undo recovery |
| Error separation | Initial-query and command failures shared state | Connection recovery clears connection errors while preserving command/backend errors |
| Publisher stop signal | Unbounded control channel | Capacity-one control channel with nonblocking stop notification |
| Sink failure | No sink | Panicking sink detaches for the session, reports last_error, and leaves authoritative counting active |

The sink runs synchronously outside the stats mutex, after counters update. It must return promptly and must not invoke listener lifecycle operations. Consumers that do heavy work need an explicit bounded handoff and overflow policy. No production synthetic parsing, per-packet Tauri events, game schema, UI redesign, charts, database, AI, or new dependencies were added. Latest raw retention remains one datagram and the event preview remains 32 bytes.

The sender process had to finish successfully; the receiver then allowed up to three seconds for missing packets, another 2.2 seconds for idle-rate checks, and joined the worker before reading the final sequence report. A failure did not prevent later cases from running.

# Historical V0.2 validation (retained with corrected SO_RCVBUF wording)
## Result

The production Rust Listener counted 1,000/1,000 datagrams at each of 10, 60, and 120 Hz using the PowerShell synthetic sender over real Windows loopback UDP. No FH6 packet layout was assumed or implemented.

## Architecture

The dedicated receiver updates authoritative session counters and retains one opaque raw datagram. A separate publisher emits a bounded statistics snapshot every approximately 250 ms. It releases the shared statistics lock before hex formatting, serialization, or Tauri delivery. React renders those snapshots and rejects stale revisions; it has no packet counter or packet-time collection.

Lifecycle calls are serialized and run through Tauri's blocking pool. Repeated starts on the active port and repeated stops are safe. Stop joins the worker and preserves totals; successful restart clears session data. Errors are captured in backend state and surfaced to React. The listener requests `SO_RCVBUF = 4 MiB`; Winsock accepted/read back 4,194,304. This is socket-option readback, not a guaranteed OS allocation or proof of actual queue capacity. The application's raw datagram allocation is bounded to 65,535 bytes and the emitted hex preview to 32 bytes.

### Failures encountered before the final pass

The first paced test, using the default receive-buffer setting, counted only 989/1,000 packets at 10 Hz (126,592 bytes; no socket errors). Development builds were active concurrently. No sequences were recorded, so neither the missing ranges nor the received tail can be reconstructed. The drop location and cause were not established. The listener was then changed to request 4 MiB, and a later suite passed; those sequential observations do not establish SO_RCVBUF as the cause or fix. A separate default Windows socket read back 65,536 for SO_RCVBUF; that value is not a measurement of allocated memory or actual queue capacity.

An earlier check also read source files mid-edit and failed because the integration test referenced the new receive-buffer field before its library build contained it. All final checks above were rerun against settled source and passed.

## Remaining risks and validation boundaries

- UDP may drop packets before the process receives them; receive-error counts cannot detect all OS/network loss. A 4 MiB SO_RCVBUF request is not a delivery guarantee, an allocation measurement, or evidence explaining the earlier loss.
- These are loopback synthetic tests at 128 bytes per packet, plus isolated maximum-size and burst tests. Real FH6 traffic, prolonged sessions, large-payload bursts, and network contention remain unverified.
- The paced test uses the exact production Listener but does not drive React or the Tauri WebView. Native start/stop clicks, frontend reload, shutdown, and actual event cadence have not been automated in this run.
- Only the latest raw packet is retained. This is not a packet recorder, and no parser or persistence was added.
- Windows was the tested platform. Other platforms may cap the requested receive buffer or schedule timeouts differently.
