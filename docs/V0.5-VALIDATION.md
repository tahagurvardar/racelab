## Connection transitions

Connection state is derived from transport readiness, detector lock, freshness, session state and recent faults. Session state is independent: `ACTIVE`, `GRACE`, or `COMPLETED`.

| Trigger | Connection result |
|---|---|
| App launches / diagnostic start begins | `STARTING`; background supervisor binds port 20440 by default |
| Bind succeeds, no packets yet | `LISTENING` (Waiting for game) |
| Any UDP arrives without a protocol lock | `PROBING` (Detecting) |
| Five consecutive valid packets, at least two timestamp advances, one source endpoint | Protocol locks; `CONNECTED_IDLE`, or immediately `SESSION_ACTIVE` if the locking packet is active |
| Locked, valid active packet | `SESSION_ACTIVE`; create session if needed |
| Active session receives inactive packet | `GRACE` immediately |
| Active session has no valid active packet for 1500 ms | `GRACE`, beginning at last active receipt + 1500 ms |
| Valid active telemetry returns strictly before grace deadline | Same session returns to `SESSION_ACTIVE`, subject to recent-fault overlay |
| Grace expires with fresh inactive telemetry | Session completes; `CONNECTED_IDLE`, subject to recent-fault overlay |
| Grace expires without fresh valid telemetry | Session completes; release protocol lock; `DISCONNECTED`, or `PROBING` if unknown packets are still arriving |
| Idle locked stream becomes stale for 1500 ms | Release lock; `DISCONNECTED`, or `PROBING` if unknown packets still arrive |
| Valid stream returns after lock was released | `PROBING`; require detection again; next active lock starts a new session |
| Locked stream has a recent invalid packet, subscriber drop or transport warning | `DEGRADED`, unless session is already in `GRACE` |
| Fault ages out, valid packets continue | Return to `CONNECTED_IDLE` / `SESSION_ACTIVE` |
| Bind/setup failure or unexpected transport termination | `ERROR`; finalize session with transport-error reason |
| Explicit diagnostic stop | `DISCONNECTED`; finalize session, suppress pending automatic start |

Priority is stopped/error, startup, unlocked probing/listening/disconnected, grace, degraded, then active/idle. Grace may coexist with degraded health. States occurring on the same packet can be too brief to appear in a sampled UI. Automatic disconnection does not stop or rebind the UDP socket. Bind failure is visible and requires a diagnostic retry after resolving the conflict; there is no endless bind retry loop.

## Detector and health

`ProtocolAdapter` provides an ID and byte-to-canonical-frame validation method. The registry supports 1..8 adapters; only FH6 is registered. Detector memory retains one candidate/source and one clock, not an accumulating source map. A source change during probing restarts its streak. Foreign sources are rejected while locked. Invalid probing packets reset the streak.

FH6 requires the supplied 324-byte layout, finite implemented float values, activity 0/1, plausible engine values, nonnegative speed matching velocity magnitude within 0.001 m/s, valid byte controls and steering -127..127. Before lock, inactive packets must also have plausible raw engine/motion fields. Zero-filled packets cannot establish a lock; after lock, valid inactive zero telemetry is accepted as unavailable canonical data.

The default threshold is five consecutive frames with at least two distinct game-clock advances. Probe confidence is streak / threshold, capped at 0.99 until lock. Locked confidence is `1 / (1 + consecutive rejected packets)` and returns to 1 after a valid packet. This is a diagnostic confidence score, not a statistical identity probability.

The current live clock policy supports FH6 u32 milliseconds. Backward jumps require an active/inactive transition or near-u32 wrap. Forward delta must not exceed receive-clock elapsed time + 2000 ms. Active timestamps frozen for more than 2500 ms fail; inactive timestamps may pause. Activity changes reset the stall watchdog. These are explicit policies with synthetic tests; game resets and rewind behavior beyond available evidence remain uncertain. A future adapter with a different clock contract will need its own timestamp policy.

Health is `LOST` without a running, locked stream; `DEGRADED` while locked but stale or faulted; otherwise `GOOD`. Invalid packets and subscriber drops affect health for 2000 ms. Transport warnings persist until listener restart. Input Hz and published valid-frame Hz use actual elapsed monotonic time, with windows of at least one second. **There is no assumed FH6 rate threshold.** The first four successful probe packets are raw-captured if recording, but are not published/countable canonical frames. Snapshot fields include both rates, invalid count, packet/valid ages, protocol/confidence, transport receive errors, and hub subscriber drops.

## Canonical contract

`TelemetryFrame` retains `active` and adds optional `game`, `vehicle_id`, and `game_timestamp_ms`. Engine RPM values, all motion vectors, position, speed, each control, and semantic gear are `Option`; absent values serialize as JSON `null`. Active zero speed, RPM or controls remain numerical zero. An inactive FH6 frame has null dynamic canonical values and retains available source metadata.

| Canonical data | Units / behavior |
|---|---|
| Speed / velocity | m/s |
| Acceleration | m/s² |
| Angular velocity | radians/s |
| Orientation | radians; x=yaw, y=pitch, z=roll |
| Position | metres; source coordinate system |
| Engine | RPM |
| Throttle, brake, clutch, handbrake | raw u8 / 255, range 0..1 |
| Steering | raw i8 / 127, range -1..1; -128 rejected |
| Vehicle ID | Positive FH6 car ordinal as string; otherwise null |
| Gear | Null until semantic mapping is validated; raw code retained |

No undocumented axis transform is applied. `sourceSpecific.fh6` preserves the raw gear, vehicle fields, unknown byte regions, dash extensions and all 32 implemented raw float fields, including inactive values. Invalid/non-finite values produce structured issues before JSON serialization. The existing offset map and physical policy are documented in [FH6-PROTOCOL.md](FH6-PROTOCOL.md). This contract supersedes V0.4 inactive zeroing.

## Hub and update cadence

```text
Frozen UDP -> PacketSink -> raw capture queue (unchanged)
                        -> detector + FH6 adapter -> TelemetryHub
                                                     | session engine
                                                     | bounded recent ring / latest
                                                     | bounded subscriber channels
UI -> one outstanding get_live_telemetry request -> latest snapshot
```

Every packet is processed at incoming rate. Once locked, every accepted frame reaches the hub and session engine. Hub storage uses shared immutable `Arc` frames: default ring 512, configurable 1..8192. Latest reads return the newest reference. Ring eviction is intentional retention turnover and has its own counter; it is not a subscriber loss.

At most 16 subscribers may each hold 1..4096 queued frames. `try_send` drops the newest delivery on overflow and increments `subscriber_drops`; this counts missed deliveries, so one frame missed by two subscribers adds two. Disconnected receivers are removed on publication. No subscriber callback, disk I/O, IPC serialization or UI processing runs while publishing. Short internal mutexes protect bounded memory operations; this is not a lock-free hard-real-time guarantee. Consumers process returned references after locks are released and must bound any storage they retain themselves.

The session engine retains only the current/most recently completed session. Ring contents and hub counters survive listener restart, while detector and live rate/packet counters restart. Ring history is never sent to the UI. Frontend polling has one outstanding IPC request, then a minimum 50 ms delay after completion: at most 20 updates/s and naturally slower under load. Pending replies are ignored on unmount. No normalized frame events accumulate behind a slow UI. Legacy raw statistics/capture events remain at 4 Hz. A 50 ms background tick advances lifecycle state without packets; incoming packets and snapshot reads also advance it.

## Session behavior and configuration

The first locked active frame starts a session even at zero speed; `isRaceOn` indicates activity, not proof that the car is moving. IDs combine an OS-random 128-bit app instance ID and increasing counter. Exposed metadata: `id`, `started_at` (nullable Unix milliseconds), `duration_ms`, `game`, `vehicle_id`, `state`, `ended_reason`, and remaining grace. Duration uses monotonic reception time and includes grace; it freezes at the precise expiry deadline, even if the next tick comes later.

Default grace is 10000 ms. Repeated inactive packets never extend its deadline. Recovery at or after the deadline creates a new session. A known vehicle/game change also finalizes the old session and creates a new one. Unknown vehicle IDs do not invent ID zero or split a known session. Explicit stop/restart and fatal transport failure complete the session. Completion metadata remains visible until the next session replaces it. No session database or automatic capture-file recording is introduced.

Set `$env:RACELAB_SESSION_GRACE_MS = '15000'` before `pnpm tauri dev` to change grace (allowed 1..120000 ms). Invalid configuration prevents startup with an explanatory error. Rust `ConnectionConfig` also validates detection threshold 3..100, silence 1..60000 ms and ring capacity 1..8192. Default port is 20440; manual diagnostic controls can select another port.

## Remaining risks and manual acceptance

- Detection establishes compatibility with the FH6 schema/invariants, not authenticated game identity. A compatible or deliberately crafted stream can match. Only one source is locked; source-port changes can require grace expiry and reprobe.
- Clock resets, rewind and high-RPM vehicles beyond the available evidence can be rejected by declared policies. Inactive all-zero traffic cannot identify a game before an active/plausible stream arrives.
- UDP cannot establish losses before reception. Raw capture drops and subscriber drops remain separate, visible counters. Slow subscribers explicitly lose deliveries; full-rate processing does not guarantee lossless downstream consumers.
- Unknown FH6 fields/gear semantics remain unknown. Session activity follows the game's activity flag and is not driving/lap analysis. Sessions do not survive app exit.
- Core native acceptance was subsequently confirmed by the user as recorded above. Diagnostic bind failure/retry has automated coverage; it was not included in the user's manual report. V0.5.1 menu/loading classification still needs its own live confirmation after the cleanup.
