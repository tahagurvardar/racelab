# V0.9 — derived session analysis

V0.9 adds a **derived analysis layer** on top of the frozen V0.8 telemetry
model. After a session completes, RaceLab reads its own frame stream and
produces `analysis.json`: driving events, turn segments and a data-quality
report. Nothing in this phase changes what canonical telemetry means.

This document is the contract. [V0.9-VALIDATION.md](V0.9-VALIDATION.md) holds
the tests, the real-session results and the manual acceptance procedure.

**V0.9 is released as `0.9.0`**, on the strength of one real FH6 acceptance
drive and the [hardening pass](V0.9-VALIDATION.md#v09-hardening-pass--first-real-fh6-acceptance)
it produced. One validation was not performed and ships as a known risk:
[cross-car slip-threshold portability](V0.9-VALIDATION.md#carried-into-v010-cross-car-slip-threshold-portability),
carried into V0.10.

## Measured, derived, heuristic

Every number RaceLab shows belongs to exactly one of three categories, and the
distinction is the point of this phase.

| | What it is | Example |
|---|---|---|
| **MEASURED** | A canonical telemetry value, carried across unchanged | `speed_mps` at the start of an event |
| **DERIVED** | A mathematical consequence of canonical values and the monotonic capture clock | an event duration, a time-weighted average speed, `d(speed)/dt` |
| **HEURISTIC** | A RaceLab-defined threshold or segmentation rule | "full throttle is throttle ≥ 0.95" |

A heuristic is a **product definition, never an automotive truth**. Every one of
them is stored inside the analysis it produced (`config`), so a result can
always be traced back to the rule that made it, and a later threshold change can
never be mistaken for a change in the recorded telemetry.

### Language RaceLab does not use

The telemetry does not mathematically establish any of these, so no event, label
or field is ever named:

> understeer · oversteer · wheelspin · wheel lock · traction loss ·
> bottoming out · bad braking · ideal line · good or poor driving ·
> a corner's left/right handedness

What RaceLab says instead is neutral and names the channel and the direction:
*high positive slip*, *high combined slip*, *high suspension compression*,
*rapid throttle lift*, *strong deceleration*, *turn segment*.

**V0.9 measures and segments. It does not coach.** There is no score, no rating
and no judgement anywhere in the output.

## Architecture

```
session completes (recorder writer thread, manifest already durable)
   └─> SessionCompletionHook            non-blocking try_send, bounded queue
        └─> AnalysisRunner              one background thread, queue depth 8
             └─> FrameStreamReader      existing version-aware reader, one record at a time
                  └─> AnalysisAccumulator   single pass, bounded memory
                       └─> SessionAnalysisV1
                            └─> analysis.json      temp file + fsync + rename
                                 └─> get_session_analysis  →  Sessions UI
```

Four properties are structural rather than best-effort:

1. **UDP ingestion never waits.** Ingestion hands frames to the recorder through
   the existing bounded drop-newest queue and never touches analysis at all.
2. **The recorder never waits.** The completion notification is one `try_send`
   on a bounded queue, issued by the writer thread *after* the frame stream has
   its footer and the manifest says `completed`.
3. **The queue is bounded.** Eight jobs. A request that does not fit is counted
   and refused; nothing is buffered without limit and no caller ever blocks.
4. **Failure is inert.** A failed analysis writes nothing, records the error in
   the runner's status, and leaves the completed session exactly as it was.

At startup RaceLab does **not** analyze historical sessions. A recording made
before V0.9 stays un-analyzed until something explicitly asks, and the Sessions
UI says so in as many words.

### What V0.9 did not touch

`ingress.rs`, `packet.rs`, `capture.rs`, `capture_format.rs`, the protocol
detection lifecycle, `SessionEngine`, `TelemetryHub`, the recorder's bounded
drop-newest queue architecture, the RLFRAMES framing version, the
`TelemetryFrame` v2 field semantics, the FH6 wheel mapping and the V1
compatibility semantics are all unchanged. The single additive change inside the
recorder is a post-finalization notification hook, described above.

There is **no `TelemetryFrame` schema v3**. Derived analysis does not belong
inside a telemetry frame and never will: a frame states what a game transmitted,
and an analysis states what RaceLab concluded from a stream of them.

## Versioning

`ANALYSIS_SCHEMA_VERSION = 2`, and it is **independent** of the three versions
V0.8 established.

| Version | Value | Moves when |
|---|---|---|
| `MANIFEST_SCHEMA_VERSION` | 1 | the manifest's own JSON shape changes |
| `FRAME_FORMAT_VERSION` | 1 | the RLFRAMES framing changes |
| `TELEMETRY_FRAME_SCHEMA_VERSION` | 2 | canonical telemetry fields change |
| `ANALYSIS_SCHEMA_VERSION` | **2** | the analysis document's shape changes |

The manifest gained no field. Storing analysis did not require touching it, so
it was not touched.

Schema 1 existed only in development: it presented slip as per-corner event
rows, which the first real acceptance session showed to be dozens of
near-duplicate records describing one maneuver. Schema 2 presents
[slip episodes](#slip-episodes) instead. Nothing was ever released on schema 1,
so there is nothing in the wild to stay compatible with, and a schema-1 file is
reported as **Unsupported** rather than silently reinterpreted with an empty
episode list. `frames.rlframes` and `manifest.json` are untouched by any of
this, so re-analysis regenerates the document from the recording.

## Storage

```
sessions/
  <session-id>/
    manifest.json        unchanged
    frames.rlframes      unchanged, never rewritten
    analysis.json        new in V0.9
```

`analysis.json` is pretty-printed JSON, because it is a document a person reads.
It is written to `analysis.json.tmp`, flushed, `sync_all`ed and renamed, so a
reader sees either no analysis or a complete one. A partially generated analysis
can never masquerade as a finished one, and a failed write leaves any previous
analysis intact.

A session remains listable and openable when `analysis.json` is missing, corrupt
or from an unsupported future schema. Each of those is its own reported state.

## The analysis document

```
SessionAnalysisV1 {
  schema_version, session_id, telemetry_frame_schema_version,
  analyzed_at_unix_ms,        // when the analysis FINISHED
  requested_at_unix_ms,       // when the session was queued, or null
  queued_ms,                  // how long it waited behind other sessions
  analysis_duration_ms,       // how long it actually took
  analyzed_by_racelab_version,
  config,            // every heuristic that produced this analysis
  coverage,          // which part of the recording was analyzed
  driving_summary,   // aggregate counters
  events,            // DrivingEventV1[]
  slip_episodes,     // SlipEpisodeV1[]
  turn_segments,     // TurnSegmentV1[]
  data_quality       // what could and could not be seen
}
```

### Units and time

- **Canonical SI throughout.** Speeds are m/s, accelerations m/s², yaw radians.
  Presentation units (km/h, degrees) are produced by
  `src/telemetry/formatting.ts`, exactly as they are for live telemetry. An
  analysis file holds canonical values only.
- **Times are session-relative monotonic milliseconds**, measured from the first
  record in the frame stream. The raw monotonic clock is a process-uptime value
  with no meaning to a reader; wall-clock time is never used for anything in
  RaceLab's timing. `coverage.first_monotonic_ms` retains the origin so an
  analysis can be traced back to the stream.
- A field that does not apply is `null`, never `0`.

## Time handling

All timing is `RecordedFrame::monotonic_ms`, the capture monotonic clock. Never
frontend time, never `Date.now()`, never the game timestamp, never a packet
count used as a duration, and never an assumed 60 Hz.

| Condition | Policy |
|---|---|
| Variable frame intervals | Each interval is measured; nothing assumes a rate |
| Duplicate / zero interval | Counted in `zero_interval_frames`, contributes to no time-weighted quantity, and never becomes the denominator of a derivative |
| Interval > `max_gap_ms` (**1000 ms**) | A telemetry gap: excluded from analyzed time, counted in `excluded_gap_count`/`_seconds`, and it **closes every open event** at the last frame that observed it |
| Inactive frame (menu, loading, pause) | Same treatment as a gap, counted separately in `inactive_interval_*` |

A long gap therefore closes active events rather than pretending the vehicle
continuously performed an action across time that was never measured. Telemetry
after the gap starts a *new* event.

`max_gap_ms` deliberately equals `session_summary::MAX_SAMPLE_GAP_MS`, so a
session's V0.6 summary and its V0.9 analysis exclude exactly the same intervals.

Interval statistics use **left-hand time weighting**: the interval between two
frames is attributed to the earlier sample's values. That is the same rule
`SummaryAccumulator` has used since V0.6, and it is the only interpretation
available without inventing interpolation between telemetry samples.

## Streaming and memory

`FrameStreamReader → AnalysisAccumulator → SessionAnalysisV1`. One pass, O(n) in
frames. The accumulator **never retains a `TelemetryFrame`** and keeps no frame
history. What it holds is:

- one previous `Sample` (the ~8 channels analysis reads, plus one `Wheels`,
  which is `Copy` and fixed size),
- 21 threshold state machines (5 global + 4 corners × 4 per-corner detectors),
- one open turn segment, holding two fixed-size statistics structs,
- the capped output lists,
- **one rolling window** of `(time, speed, throttle)` triples.

That window is the only history in the engine. It is trimmed to twice the
longest configured window — `acceleration_window_ms` and
`throttle_lift_window_ms` are both 250 ms, so **500 ms is retained** — and hard
capped at **256 samples**. At the ~72 Hz FH6 sends, 500 ms is about 36 samples;
the cap exists only so an implausibly fast source cannot grow it.

Measured on a real 11,006-frame session whose `frames.rlframes` is 32 MB: peak
working set **4.5 MB**. See [V0.9-VALIDATION.md](V0.9-VALIDATION.md#performance).

## Event definitions

Every event carries its bounds, its duration, the entry/exit/min/max speed it
observed, the max RPM, and the peak value of the channel that defines it. Times
are session-relative. `peak` is the magnitude and `signed_peak` the same reading
with its sign, where the sign carries information RaceLab does not interpret.

### Hysteresis

Every latched detector has an **enter** and an **exit** threshold. A value
hovering on one boundary cannot produce a stream of events, because once open a
detector stays open until the value falls past the *lower* exit threshold. On
top of that, an event shorter than its minimum duration is discarded as frame
noise.

| Event | Enter | Exit | Minimum duration |
|---|---|---|---|
| `full_throttle` | throttle ≥ **0.95** | throttle < 0.90 | 80 ms |
| `braking` | brake > **0.05** | brake ≤ 0.02 | 80 ms |
| `hard_braking` | brake ≥ **0.80** | brake < 0.70 | 80 ms |
| `strong_acceleration` | a ≥ **+4.0 m/s²** | a < +3.0 | 80 ms |
| `strong_deceleration` | a ≤ **−6.0 m/s²** | a > −4.5 | 80 ms |
| `high_suspension_compression` | travel ≥ **0.95** | < 0.90 | 250 ms |
| `high_suspension_extension` | travel ≤ **0.05** | > 0.10 | 250 ms |

Slip has no row here because slip is **not** presented as per-corner events —
see [slip episodes](#slip-episodes). Its per-corner thresholds
(`|slip ratio| ≥ 1.0`, exit 0.7; `combined slip ≥ 1.0`, exit 0.7; 120 ms) still
exist as detectors and their counts survive as data quality.

Suspension additionally uses a **150 ms merge gap**: a corner that re-crosses
its threshold within 150 ms of leaving it continues the same excursion rather
than starting a new one. Without it, washboard surface produces one event per
bump on the same wheel. The 250 ms minimum and the merge gap together are the
V0.9 hardening fix for suspension chatter; the evidence is in
[V0.9-VALIDATION.md](V0.9-VALIDATION.md#suspension-chatter).

`full_throttle`'s enter threshold and `braking`'s are deliberately identical to
the V0.6 session-summary definitions, so a session's summary and its analysis
never disagree about what full throttle was.

**None of these numbers is a motorsport standard.** 0.80 is not an industry
definition of hard braking; it is what RaceLab calls hard braking in V0.9.

### `rapid_throttle_lift`

The one event that is not a latch. A throttle fall from **≥ 0.80 to ≤ 0.20**
inside a **250 ms** window is reported once, from the sample holding the high
value to the sample holding the low one. A **500 ms cooldown** stops one pedal
movement being reported twice; that cooldown plus the from/to pair is this
event's anti-chatter rule, in place of a minimum duration. Its duration is
therefore genuinely short — it measures how fast the pedal moved — and can be a
single frame interval.

A throttle that falls slowly, outside the window, is not a lift.

### Longitudinal acceleration

**Derived from canonical speed and monotonic time only:**
`a = Δspeed / Δt`, in m/s², differenced over at least **250 ms** so a single
noisy speed sample cannot produce a large value.

The source acceleration vector is deliberately **not** used. V0.8 established
`+Z` is forward by correlation, but that was a measurement used to *identify*
fields during an audit — it never became a runtime rule, and naming one of that
vector's components "longitudinal" would be an unproven claim. `d(speed)/dt` is
a derivative of two proven quantities and asserts nothing else.

A negative acceleration is reported as **deceleration, never as braking**.
Braking is a separate event driven by the brake channel, and the two are
independent: a car slowing with no brake input produces a deceleration event and
no braking event.

#### Speed discontinuities

A \|Δspeed/Δt\| beyond **50 m/s² (≈ 5.1 g)** is treated as a **discontinuity in
the recorded speed**, not as vehicle acceleration. A collision, a respawn, a
rewind and fast travel all move the car's speed without the car having
accelerated, and no road or race car sustains 5 g under its own tyres.

RaceLab does not claim to know which of those happened. The sample is excluded
from acceleration events and from the summary extremes, and counted in
`data_quality.speed_discontinuities`. **Nothing is clamped and nothing is
repaired** — the recorded telemetry is untouched, exactly as V0.8's
"report, never repair" rule requires.

This rule was added because real captures produced a derived **−203 m/s²** —
about 20 g — which is a true derivative of what was recorded and a false
statement about how the car was driven.

### Suspension events

Suspension uses `normalized_suspension_travel`, whose V0.8 meaning is
established: **0 is full extension (droop), 1 is full compression**. RaceLab
therefore reports *high compression* and *high extension* and nothing more.

Corner identity comes from the latch's own `WheelPosition`, and the value from
`Wheels::get` on that same position. Analysis never reorders wheels and never
indexes them positionally.

### Output caps

`max_events` is **400 per kind**, `max_slip_episodes` is **200** and
`max_turn_segments` is **200**. The event cap is per kind so one noisy channel
cannot crowd every other event out of the file. Anything beyond a cap is still
counted in `driving_summary` and reported in `data_quality.events_truncated`,
`slip_episodes_truncated` or `turn_segments_truncated`; nothing is silently
dropped.

## Slip episodes

One maneuver puts several corners over threshold on **both** slip channels at
overlapping but not identical times. Reporting each corner and each channel as
its own row produced, in the first real acceptance session, **220 near-duplicate
records describing one drive**. That is a presentation failure, not a detection
failure: the detectors were right, the rows were redundant.

So slip is presented as a **coalesced episode**:

- While any corner is over threshold on either channel, an episode is open.
- It stays open across quiet stretches shorter than **`slip_merge_gap_ms`
  (400 ms)**. A longer stretch is a clearly distinct period of normal grip and
  ends the episode.
- An episode is reported only when the time actually spent above threshold
  reaches **`slip_min_ms` (120 ms)**. That is *engaged* time, not span: a
  channel flickering over the threshold every other frame accumulates no engaged
  time and cannot become an episode.
- A gap, an inactive frame or the end of the stream closes it, exactly as for
  every other detector.

Each episode keeps, **per affected corner**, the maximum absolute slip ratio,
the signed value at that maximum, and the maximum combined slip — plus the
affected corners, the channels involved, and entry/min/max/exit speed.

**Coalescing changes how many rows describe a maneuver, never what the maneuver
measured.** No peak is discarded, and a large slip value is never clamped or
suppressed for being large. Real sessions reach `|slip_ratio|` above 70 and the
episode reports that number.

The neutral term is deliberate: this is a *high slip episode*, never wheelspin,
wheel lock, traction loss, a slide or a mistake.

### The raw detector counts survive as diagnostics

`data_quality.slip_ratio_detector_events` and
`combined_slip_detector_events` count the per-corner engagements that lasted at
least `slip_min_ms`, before coalescing. They are **diagnostics, not driving
events**. Far more of them than episodes is the normal, expected shape of one
maneuver lighting up several corners at once, and the UI shows both numbers side
by side so that ratio is visible rather than hidden.

`driving_summary.slip_episode_seconds`, read against
`coverage.analyzed_seconds`, says how much of the drive the slip thresholds
actually selected. When that share is large, the honest reading is that the car
really was slipping for most of the drive — which a fixed threshold cannot
distinguish from a threshold that is mis-scaled for that car. See
[the portability limitation](V0.9-VALIDATION.md#slip-threshold-portability).

## Turn segmentation

A **turn segment is not a claim about a track corner.** RaceLab has no track
model, no map and no lap geometry. A segment is the interval during which the
recorded yaw rate stayed above a RaceLab threshold while the car was moving
above a RaceLab minimum speed.

Yaw rate is the **wrap-corrected** difference of canonical yaw
(`orientation.x`, radians) over the monotonic interval:

```
rate = wrap(yaw - previous_yaw) / Δt      wrap maps into (-π, π]
```

Without the correction a yaw crossing from `+π` to `-π` would read as a half
revolution in one frame. The correction assumes only that the car cannot rotate
more than half a revolution between consecutive samples, which at any plausible
frame interval it cannot.

### Gating

| Gate | Default |
|---|---|
| Minimum speed | **5.0 m/s** |
| Enter | \|yaw rate\| ≥ **0.20 rad/s** |
| Exit | \|yaw rate\| < **0.10 rad/s** |
| Exit hold | **250 ms** continuously below exit |
| Minimum segment duration | **600 ms** |
| Minimum net heading change | **0.20 rad** (≈ 11.5°) |

A segment closes when the yaw rate has stayed under the exit threshold for the
hold window, when the rate **reverses direction** past the enter threshold
(which is what keeps a left–right pair two segments rather than one), or when a
gap, an inactive frame or the end of the stream intervenes.

### Why a net heading change is required

Yaw *rate* alone cannot tell a gentle curve from a second of steering correction
that ends where it started: both cross the rate threshold, and both can last
longer than the minimum duration. The first real acceptance session produced two
such segments, 845 ms and 775 ms long, whose net heading changes were **0.040
rad (2.3°)** and **0.057 rad (3.3°)** — the car had not turned.

A segment must therefore satisfy the duration, speed and yaw-rate conditions
**and** change the car's heading by at least `turn_min_abs_yaw_change_rad`. This
is **not a physical corner threshold**; it is a RaceLab rule about what is worth
calling a segment. Wraparound correction, direction-reversal splitting, gap
behaviour and the speed gate are all unchanged by it.

A segment **ends at its last engaged sample**, not at the end of the hold
window. Statistics accumulated during the hold are buffered in a fixed-size
pending struct and merged only if the segment resumes, so a segment's reported
duration, speeds and pedal times contain no straight-line running.

### What a segment carries

Start, end, duration, signed yaw change, mean and peak yaw rate, entry / minimum
/ exit / maximum / time-weighted-average speed, brake time, throttle time,
full-throttle time, max brake input, and per named corner the maximum absolute
slip ratio, maximum combined slip and maximum suspension compression.

### Left and right

`signed_yaw_change_rad` is stored because it is a real measurement. The mapping
from its **sign to the driver's left or right is a parity bit that kinematics
cannot supply** — the same class of fact as the wheel-order parity bit V0.8
documented — and it has **not** been validated in-game.

Presentation therefore labels segments **"Turn segment N"**, in time order, and
never "left" or "right". The signed yaw change is shown, in degrees, with its
sign intact. If manual acceptance establishes the sign convention, adding the
label is a presentation change and this section is where it gets recorded.

## Data quality and graceful degradation

`data_quality` reports `frames_read`, `active_frames`, `inactive_frames`,
`zero_interval_frames`, `speed_discontinuities`, `frame_stream_complete`, the
telemetry frame schema version, per-channel availability
(`speed`, `controls`, `engine`, `orientation`, `wheel_telemetry`,
`suspension`), and the truncation counters.

`coverage` reports the monotonic span, `recorded_seconds`, `analyzed_seconds`,
and the excluded gap and inactive-interval counts and durations.

**A missing channel never invalidates an analysis.** It makes the events that
depend on it unavailable, and the UI says which channel and why.

A frame stream with no footer — a session lost to a crash — is still analyzed.
It reports `frame_stream_complete: false` rather than being refused.

## V1 and V2 sessions

The analyzer uses the **existing version-aware `FrameStreamReader`**, so nothing
about schema handling is new or duplicated.

| | schema v1 recording | schema v2 recording |
|---|---|---|
| Speed-derived acceleration | yes | yes |
| Throttle / brake events | yes | yes |
| Turn segmentation | yes (V1 carried orientation) | yes |
| Slip events | **unavailable** | yes |
| Suspension events | **unavailable** | yes |
| Per-corner turn peaks | **null** | yes |

V2-only channels are reported as *unavailable*, never as zero.

**No V2 field is reconstructed from a V1 recording's `sourceSpecific`
envelope**, even where the bytes are sitting right there. That envelope was
written before the V2 canonical contract existed and was never validated against
it; mining it would manufacture data nobody checked. This is asserted by a test
that puts slip 9.0 and travel 1.0 on all four wheels inside a V1 envelope and
requires that no wheel event and no per-corner peak appears.

**No old recording is ever rewritten.** A test byte-compares the frame file
before and after analysis.

## Backend API

| Command | Returns |
|---|---|
| `get_session_analysis(session_id)` | `SessionAnalysisState`: one of `available`, `pending`, `absent`, `corrupt`, `unsupported`, `error`, carrying the analysis only in `available` |
| `get_analysis_status()` | Runner counters: pending, analyzed, failed, rejected, last error |
| `reanalyze_session(session_id)` | Development only. Queues a re-analysis. The product flow is automatic and no UI offers this. |

Session identifiers are validated with the existing `is_safe_session_id`, so a
crafted identifier can never escape the sessions root.

**The frame stream is still never exposed to React.** There is no command that
would return frames, and the analysis document is events and segments the
backend already reduced.

## Analysis timing

`analyzed_at_unix_ms` is when the analysis **finished**, not when it was
requested. One worker runs jobs in order, so a session that completes while
another session is being analyzed waits for it. That is the bounded queue
working as designed, and it means the wall-clock gap between a session ending
and its `analysis.json` appearing is **not** a measure of how long the analysis
took.

The document therefore records both numbers separately:

| Field | Meaning |
|---|---|
| `requested_at_unix_ms` | when the completed session was queued; `null` for an offline analysis |
| `queued_ms` | how long the job waited before starting |
| `analysis_duration_ms` | how long the analysis itself took |

`AnalysisRunnerStatus` carries `last_queued_ms` and `max_queued_ms` alongside
`last_duration_ms` for the same reason. The first real acceptance session showed
exactly why: see
[the delay investigation](V0.9-VALIDATION.md#the-55-second-analysis-delay).

When analysis is unavailable, pending, unsupported or corrupt, the section shows
that state explicitly. **An absent analysis is never rendered as zero events**;
the UI says so in as many words, because "no analysis has run" and "analysis ran
and found nothing" are different statements.
