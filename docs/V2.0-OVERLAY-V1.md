## Architecture and operation

`overlay.html` loads its own small React root. It never mounts `App`, the main
stores, session controllers, recorder hooks or main telemetry owners. Vite builds
both production entry points; the `review/` harness remains development-only.

The Rust `OverlayService` receives the existing `Arc<F1EvidenceService>` and
`Arc<Appliance>`. Its worker reads the same compact `live_status()` API as
`get_f1_live`, caching one latest sample at approximately 10 Hz. It creates no
listener, recorder or history. `get_overlay_frame` copies that bounded cache;
the separate webview has one completion-paced 100 ms reader. A separate 100 ms
paint/freshness watchdog expires readings even if an IPC call hangs. There is at
most one queued main-thread window job. Settings reads coarse window state at
1 Hz and changes its child only when that state changes; it never reads frames.

The overlay window is created once, initially hidden/unfocused. Play shows on
fresh player Car Telemetry, holds through brief staleness, and hides after its
established three-second family cutoff. It also hides when disabled, the F1
listener/player is unavailable, or FH6 has fresh active driving telemetry.
Main minimization is absent from this decision. Main close requests application
exit, and shutdown stops/joins the overlay worker with the existing services.

## Windows input and focus

The shared Tauri builder uses transparency, decorations off, shadow off,
always-on-top, taskbar exclusion, `focused(false)` and `focusable(false)`.
Play also uses `set_ignore_cursor_events(true)` and disables resizing.

All HWND access lives in `overlay_windows.rs`. It verifies the effective native
styles rather than trusting an always-on-top setting:

| Property                                 | Play    | Edit    |
| ---------------------------------------- | ------- | ------- |
| `WS_EX_TOPMOST` / `HWND_TOPMOST`         | On      | On      |
| `WS_EX_TOOLWINDOW`, no `WS_EX_APPWINDOW` | On      | On      |
| `WS_EX_LAYERED`                          | On      | On      |
| `WS_EX_TRANSPARENT`                      | On      | Off     |
| `WS_EX_NOACTIVATE`                       | On      | Off     |
| `WS_CAPTION`                             | Cleared | Cleared |
| Tauri focusable / resizable              | Off     | On      |

Showing uses `SetWindowPos` with `SWP_NOACTIVATE`, never `SetForegroundWindow`.
Layered compositing is initialized with `SetLayeredWindowAttributes`; CSS applies
the user's opacity. Tao retains caption bits for custom non-client handling, so
the adapter explicitly clears them and verifies the result. Native failures hide
the window and surface in Settings. No injection, hooks, graphics interception,
game process access or game memory reading is involved.

This uses the documented [Tauri window builder](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewWindowBuilder.html),
[Tauri cursor-event API](https://v2.tauri.app/reference/javascript/api/namespacewindow/#setignorecursorevents),
[Microsoft extended styles](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles),
[layered-window input routing](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#layered-windows),
and [SetWindowPos activation flags](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos).
The Windows SDK bindings supply constants; none are guessed numeric flags.

## Settings, placement and data

Settings adds Show in-game overlay, Edit position / Finish editing, Scale and
Opacity. Edit has a labeled drag header and a lower-right resize gesture. Main
Settings also offers keyboard-operable position buttons. Finish restores Play;
turning the overlay off ends editing. Edit previews missing telemetry with
dashes, but remains hidden while FH6 is actively driving.

The additive `overlay` section stores enabled, physical desktop x/y, unscaled
logical client width/height, scale and opacity. Old files default to disabled,
440 × 210 logical pixels, 100% scale and 90% opacity. Size, finite values,
75–150% scale and 30–100% opacity are validated. Invalid overlay sections fall
back independently without discarding storage budget or first-detection fields.
Existing schema version, storage environment precedence and first-run semantics
remain intact. Saves are atomic and serialized; edit geometry is debounced
500 ms on the worker, with a final save on shutdown. Edit mode itself is not
persisted, so every launch begins in Play.

Placement uses actual monitor bounds, including negative desktop origins and
each monitor's DPI. A removed/off-screen saved position recovers onto an
available display, primary first. Logical size and user scale remain separate
from OS DPI. Play periodically checks monitor availability and native styles;
unchanged geometry does not cause repeated show/hide operations. Very small
displays may constrain the client size; the placement remains recoverable from
main Settings. Physical mixed-DPI monitor transitions still need final manual QA.

The eleven readings are gear (R/N/1–8), speed (km/h), actual RPM, throttle and
brake (%), lap, sector, position, actual DRS ON/OFF, ERS store (MJ) and fuel.
DRS allowed is never substituted for actual DRS. ERS is joules ÷ 1,000,000;
there is no invented capacity percentage or strategy. Fuel keeps the existing
model's factual value without inventing a unit. Each reading follows its own
Phase C family: fresh ≤1,000 ms; stale ≤3,000 ms, dimmed with “Not updating”;
unavailable afterwards, replaced by a dash. Car Telemetry expiry hides Play.
Cached sample age and local elapsed time are both included; no interpolation.

Target modes are Windows windowed and borderless-windowed. Visibility over an
actual F1 game remains a manual gate. True exclusive fullscreen, other topmost
surfaces, protected desktops and compositor-specific behavior are not promised.

## Reproduce without a game

Run `pnpm dev`, then open `/review/overlay.html?scenario=f1-live`.
`f1=stationary|driving|braking|high-speed` uses the reviewed real golden snapshots.
Overlay-only variants: `overlay=stale|unavailable|disabled`, `gear=R|N|8`,
`scale=1|1.25|1.5`, `edit=1`, `drs=on`, `long=1`.
DRS ON, gear overrides and limit values are **synthetic UI states**, not
live-game transition evidence. Main-window fixtures remain unchanged.

With Vite on port 1420, run:

```powershell
cargo run --manifest-path src-tauri/Cargo.toml --example overlay-window-check
```

This uses the production window/controller, real WebView2, isolated temporary
settings, one existing F1 service on an ephemeral port, and unchanged captured
datagrams replayed at 20 Hz. It creates no recorder. The example receives the
same Tauri-generated Windows Common Controls/DPI manifest through `build.rs`.
Optional `RACELAB_OVERLAY_CHECK_REPORT` writes its JSON result to a chosen file.
