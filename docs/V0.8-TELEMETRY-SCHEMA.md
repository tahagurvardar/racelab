# V0.8 — canonical TelemetryFrame schema v2

`TelemetryFrame` is RaceLab's game-independent model. V0.8 expands it from
schema version 1 to **schema version 2** and makes stored recordings
version-aware. This document is the contract; [V0.8-VALIDATION.md](V0.8-VALIDATION.md)
holds the evidence that justifies every field in it, and
[FH6-PROTOCOL.md](FH6-PROTOCOL.md) holds the FH6 offsets it is decoded from.

## Version numbers, and which of them moved

Three versions are stored and they are deliberately independent.

| Version | V0.7 | V0.8 | Moves when |
|---|---|---|---|
| `MANIFEST_SCHEMA_VERSION` | 1 | **1** | the manifest's own JSON shape changes |
| `FRAME_FORMAT_VERSION` (RLFRAMES container framing) | 1 | **1** | the magic, header layout or record envelope changes |
| `TELEMETRY_FRAME_SCHEMA_VERSION` (canonical frame payload) | 1 | **2** | canonical fields change |

Only the canonical payload changed in V0.8, so only its version moved. The
manifest gained no field and the container framing is byte-identical, so
bumping either would have invalidated readable files for no reason.

`SUPPORTED_TELEMETRY_FRAME_SCHEMA_VERSIONS` is `[1, 2]`. This build **writes 2**
and **reads 1 and 2**. Any other value is rejected with a message naming the
version — never decoded on a best-effort basis.

## Canonical shape

Two conventions hold throughout, in Rust and in the TypeScript mirror:

1. **Every leaf measurement is optional.** `None`/`null` means *unavailable*,
   and is never the same thing as a measured zero.
2. **Container structs are always structurally present.** An unavailable group
   is the container with every leaf null. This is how `Engine` and `Controls`
   already behaved in schema v1, and `Vehicle`, `Wheels` and `Race` follow it.

```
TelemetryFrame {
  active, game, vehicle_id, game_timestamp_ms      // unchanged from v1
  engine: Engine { rpm, idle_rpm, max_rpm,
                   power_w, torque_nm }            // + two fields in v2
  acceleration, velocity, angular_velocity,
  orientation, position, speed_mps                 // unchanged from v1
  controls: Controls { … }                          // unchanged from v1
  gear                                              // unchanged from v1; FH6 leaves it null
  vehicle: Vehicle { class_code, performance_index,
                     drivetrain_code, cylinders }   // new in v2
  wheels: Wheels { front_left, front_right,
                   rear_left, rear_right }          // new in v2
  race: Race { lap_number, race_position,
               race_time_seconds }                  // new in v2
  sourceSpecific                                    // unchanged from v1
}

Wheel {
  temperature_c, slip_ratio, slip_angle, combined_slip,
  rotation_rad_s, normalized_suspension_travel, suspension_travel_m
}
```

### A field that is not established is absent, not permanently null

Schema v2 has no `boost`, no `fuel`, no `best_lap_seconds` and no
`distance_traveled_m`. FH6 transmits all of them and the adapter preserves all
of them, but none has established semantics, so none is a canonical field.

This is a deliberate choice over declaring them and leaving them forever null.
A null field means "this frame does not carry a value"; a field that can never
carry a value is a different statement, and the honest way to make it is not to
have the field. When the evidence arrives, adding it is a schema v3 bump — which
is cheap now that version-aware reading exists.

## Canonical unit rules

- A field name carries a unit suffix **only when that unit is established**.
  `power_w`, `torque_nm`, `temperature_c`, `rotation_rad_s`,
  `suspension_travel_m` and `race_time_seconds` all assert their unit and all
  have evidence for it.
- A dimensionless source quantity gets no suffix. `slip_ratio`, `slip_angle`
  and `combined_slip` are normalized source values whose normalization domain is
  not established. `slip_angle` in particular is **not** an angle in radians:
  the observed range rules that out, so it must never be named `slip_angle_rad`.
- A code gets a `_code` suffix and is never turned into a name.
  `class_code` and `drivetrain_code` are integers RaceLab does not interpret.
- **All unit conversion happens in the adapter.** FH6 sends tire temperature in
  Fahrenheit; the adapter converts once and the canonical value is Celsius. No
  conversion of a source unit happens anywhere else, and never in React.
- Presentation conversions are a separate thing and live in
  `src/telemetry/formatting.ts`: km/h from m/s, kW from W, mm from m, rpm from
  rad/s. They are exact arithmetic on an already-canonical value and they never
  change what is stored.

## Wheel order

Corner identity is resolved **once**, by `adapters::fh6::WHEEL_ORDER`, which
maps a source wheel-block index to a `WheelPosition`. Every per-wheel block in
the FH6 packet is four consecutive `f32` at `base + 4 * index`, and the mapping
is:

| Source index | Canonical corner |
|---|---|
| 0 | `FrontLeft` |
| 1 | `FrontRight` |
| 2 | `RearLeft` |
| 3 | `RearRight` |

Everything downstream reads **named corners**. `Wheels` has four named fields
rather than an array, so a corner cannot be transposed by an index slip in
serialization, in storage or in the UI. The frontend maps a corner code to a
field name in exactly one place (`CORNER_FIELDS` in
`src/telemetry/telemetry-view-model.ts`) and an architecture test fails if a
second module ever repeats that mapping.

The evidence for this ordering — including the one bit that is provably not
derivable from telemetry — is in
[V0.8-VALIDATION.md](V0.8-VALIDATION.md#wheel-order).

## Null and unavailable policy

- An inactive (menu/loading) FH6 packet produces a frame whose `engine`,
  `wheels`, `race` and dynamic vectors are entirely unavailable. The game
  timestamp survives, and every raw value stays in `sourceSpecific`.
- Vehicle configuration codes use the same guard the vehicle identifier already
  used: they are available only when the car ordinal is positive. A zero-filled
  menu packet therefore reports *no vehicle* rather than a class 0 car with 0
  cylinders.
- A value that fails validation is **reported, never repaired**. Nothing is
  clamped into range and nothing is replaced with a plausible substitute.

## Semantic validation added in V0.8

Each rule follows from the field's own definition rather than from an observed
range, so it holds for any vehicle:

| Field | Policy |
|---|---|
| `normalized_suspension_travel` | within `0..=1` — a *normalized* value outside its normalization is self-contradictory |
| `combined_slip` | non-negative — it is a magnitude |
| `race_time_seconds` | non-negative — it is elapsed time |

These join the existing V0.4 speed/velocity and RPM policies. All 18,165
captured packets satisfy them. They report through the same `Issue` mechanism
as every other rule, so packet classification is unchanged: a packet with an
issue is withheld from the live display exactly as an implausible RPM already
was.

The measured invariant `combined_slip == hypot(slip_ratio, slip_angle)` is
**reported by the offline validator and never enforced at runtime**. It is the
measurement that identified the three slip blocks, not a guarantee the protocol
makes, and a future game patch changing it should produce a reviewed decision
rather than a stream of rejected packets.

## V1 → V2 compatibility

Recordings made by V0.6 and V0.7 carry `telemetry_frame_schema_version = 1`.
They stay readable, and **nothing on disk is ever rewritten or migrated**.

- `src-tauri/src/telemetry_v1.rs` holds `TelemetryFrameV1` and `StoredFrameV1`:
  a **frozen** copy of the exact V1 serialized shape. These types must never be
  edited to follow a later schema — doing so would silently reinterpret data
  already written.
- `session_format::decode_record` is the single place a stored schema version
  becomes a current frame. Schema 2 decodes directly; schema 1 decodes through
  the frozen structs and converts.
- The conversion is **faithful, not reconstructive**. Every V1 value is carried
  across unchanged. Every field introduced by V2 becomes `None`.
- In particular, canonical V2 fields are **not** reconstructed from a V1
  recording's `sourceSpecific` envelope, even where the bytes are sitting right
  there. That envelope was written before the V2 canonical contract existed and
  was never validated against it, so mining it would manufacture data that was
  never checked.

Callers never branch on a stored schema version: `read_all_frames` and
`FrameStreamReader::next_frame` both hand back current-shape records whatever
the file says.

### Manifest compatibility

`SessionManifestV1` is unchanged, so its `schema_version` stays 1. Its
`telemetry_frame_schema_version` field now describes a stream that may be v1 or
v2, and `read_manifest` accepts either. Recent Sessions and Session Details are
served from the manifest alone and never open a frame file, so both work
identically for an old and a new recording.

An unsupported telemetry schema version makes that one session unreadable — it
is skipped from the listing and counted in `unreadable` — without taking the
rest of the listing down with it.

## What V0.8 did not change

The recorder's concurrency architecture is untouched: the same bounded
drop-newest queue, the same non-blocking ingestion, the same background writer,
the same checkpoint cadence, the same crash-safety and drop semantics. The only
change is the schema version it writes into the header and the manifest.

Session summary semantics are also unchanged. `distance_meters` is still speed
integrated over monotonic frame time and is explicitly *not* the game's own
distance counter — see [V0.8-VALIDATION.md](V0.8-VALIDATION.md#session-summary)
for why that counter was not adopted.
