# V0.10 — FH6 product hardening

The contract for the four product behaviours V0.10 adds: bounded storage,
interrupted-session recovery, the analysis job state model, and re-analysis.

V0.9 semantics are otherwise unchanged. `TelemetryFrame` is still schema 2,
RLFRAMES framing is still version 1, `SessionEngine` is still the sole lifecycle
authority, and there is still no manual Start Recording or Start Listener
control anywhere in the product.

---

## 1. Storage retention

### The policy, in one sentence

> When the sessions directory exceeds its budget, RaceLab deletes whole
> sessions, oldest first by start time, until it is under budget again. It never
> deletes the session being recorded, a session waiting for or undergoing
> analysis, or a session it cannot identify.

### Why a bound is necessary

A normalized recording costs about 3 KB per frame at 75 Hz — roughly 0.8 GB per
hour. The evidence corpus on the development machine holds 1.45 GB across 45
sessions, one of which is a single 78-minute drive occupying 1,015 MB.

Without a bound the only thing that stops RaceLab filling a disk is the disk
being full, and the recording that fails at that moment is the one being made
*right now*. Retention is therefore not housekeeping: it is what keeps the
current session recordable.

### Configuration

| Setting | Value |
| --- | --- |
| Default budget | 8 GiB (`DEFAULT_STORAGE_BUDGET_BYTES`) |
| Override | `RACELAB_STORAGE_BUDGET_BYTES`, a whole number of bytes |
| Disable deletion | set the override to `0` |

8 GiB is roughly eight hours of continuous recording. An unparseable override is
an error at startup rather than a silent fallback, because silently ignoring a
storage setting is how a disk fills up.

With deletion disabled, usage is still measured and reported. A user who turned
retention off still deserves to be told how much disk their recordings use.

### What is protected

Protection is asked for **at the moment of deletion**, not when the sweep was
planned, so a session that starts recording midway through a sweep is still
safe.

| Protection | Source |
| --- | --- |
| The session being recorded or finalized | `SessionRecorder` |
| A session queued for analysis | `AnalysisRunner` |
| A session being analyzed | `AnalysisRunner` |
| A manifest still marked `recording` | the manifest itself |
| A session whose manifest cannot be read | see below |

A directory whose manifest cannot be parsed has **no established start time**,
so oldest-first cannot honestly place it in the order. It is never chosen for
deletion. Its bytes are still counted and reported separately as
`unidentifiable_bytes`, so a corrupt session holding the budget down is visible
rather than mysterious.

A folder whose name is not a valid session identifier is not a session at all.
It is neither counted nor deleted, whatever it contains.

### How a deletion is made

The directory is renamed to `<id>.rl-deleting` and only then removed. The rename
is atomic, so a session is never observable in a half-deleted state where its
manifest survives its frames. The marker name contains a `.`, which
`is_safe_session_id` rejects, so no listing can mistake it for a session.

A leftover marker — a rename that succeeded followed by a removal that did not,
which on Windows means a file something else still has open — is retried by the
next sweep.

### No silent data loss

Every deletion is counted (`deleted_sessions`), every byte reclaimed is counted
(`reclaimed_bytes`), and every failure is counted (`failed_deletions`) and
reported (`last_error`). The Sessions view states usage against the budget on
every visit, names any deletions made this run, and says so explicitly when the
budget cannot be met because the sessions that would be next are still in use.

### Ingestion never waits

Every byte of directory work happens on the retention thread. The UDP path, the
hub and the recorder's writer thread never call into retention; they only hand
it a wakeup through a one-slot channel that cannot block. Sweeps are requested
when a session completes and when an analysis job finishes — the latter because
a finished analysis releases a session retention was protecting, which is what
lets the budget converge when the oldest sessions are the queued ones.

## 2. Interrupted-session recovery

### The problem

A recording that ends because RaceLab stopped leaves two artefacts that
disagree. `frames.rlframes` is append-only and holds every record that reached
the disk. `manifest.json` holds the last five-second checkpoint, which can be
minutes behind.

This is not hypothetical. Twelve sessions in the evidence corpus report
`frame_count: 0` beside frame files of 0.9 MB to 43.6 MB, because they were
recorded before the manifest was checkpointed at all. Reading only the manifest
reports a session that captured nothing.

### What recovery does

It reads the frame stream and reports what is there. It never writes
`frames.rlframes` — not repaired, not truncated, not re-encoded.

| Outcome | Meaning |
| --- | --- |
| `pending` | Recognised as interrupted; not yet scanned. |
| `complete` | Every record read cleanly and the stream carried its footer. |
| `truncated` | Records read cleanly up to a point, then the file stopped. |
| `damaged` | A record in the middle could not be decoded. |
| `unreadable` | The stream could not be opened or its header was unreadable. |

`truncated` is the ordinary shape of a crashed recording: a process killed
between two `write_all` calls leaves its final record incomplete. Every complete
record before it is intact and was always readable.

### Startup, in two halves

1. **Synchronous, manifest-sized.** A manifest still marked `recording` is
   reclassified as `interrupted`, loses any summary, and is marked
   `recovery: pending`. No frame is read. This runs inside the recorder's
   constructor, before any new session can be opened.
2. **Background.** The recovery thread scans each pending session and records
   what it found. A 1 GB frame stream takes seconds to read, and neither startup
   nor UDP ingestion may wait for it. The scan is streaming and bounded to one
   record of memory.

A session whose recovery record is already finished is never rescanned: the
frame stream cannot change, so the answer cannot either. A completed session is
never touched.

### What recovery may change in a manifest

`SessionManifestV1` gains one optional field, `recovery`, carrying the record
above. Applying a finished scan may additionally **raise** `frame_count`,
`active_frame_count`, `inactive_frame_count`, `duration_us` and
`ended_at_unix_ms` to what the file actually holds.

Raising is safe in a way lowering is not: a checkpoint can only ever
under-report, so raising it to the measured value never destroys information.
The guard is one-directional — a manifest that already claims *more* than the
scan could read keeps its own number, and the disagreement stays visible in the
recovery record rather than being quietly resolved downwards.

**`status` is never changed by recovery.** An interrupted session stays
interrupted forever and never gains a summary, however much of it recovered.
"Its telemetry is intact" and "it is a finished session" are different
statements and RaceLab makes only the first.

### Analysis of a recovered session

Analysis reads a session only when it has **safely readable coverage**:

- a completed session always qualifies;
- an interrupted session qualifies once a scan has established a readable
  prefix, and never before — analyzing a session nothing has inspected would be
  guessing about its contents;
- a session still being recorded never qualifies, because its frame file is open
  and growing.

The analyzer reads with `next_frame_lossy`, which ends the stream at a truncated
tail instead of failing it. Tolerance stops exactly there: a corrupt payload, an
unknown record tag or an over-long length is still an error. The rule is that a
file which *stops* is analyzed up to where it stops, and a file which is *wrong*
is refused. An analysis produced from a truncated stream reports
`frame_stream_complete: false` and can never look like a complete recording.

## 3. Analysis job state

Six states, each of which is a different thing to tell a user:

| State | Meaning |
| --- | --- |
| `not_analyzed` | No analysis and no job. The normal state of a pre-V0.9 recording. |
| `queued` | Requested, waiting for the worker. |
| `analyzing` | Being analyzed now. |
| `available` | A readable analysis of a supported schema. |
| `failed` | Attempted and produced no readable result. |
| `unsupported_schema` | Written by a schema this build cannot read. |

V0.9 collapsed `queued` and `analyzing` into one "pending", which meant a
session waiting behind a long analysis was indistinguishable from one being
worked on. It also reported a *failed* analysis as an absence, which is a silent
failure — the one outcome this model exists to prevent.

### Diagnostics

Bounded and deliberately product-shaped: `queued_ms`, `analysis_duration_ms`,
and a `failure_reason` where one applies. Queue wait and analysis time are
separate numbers and are never summed: a short session finishing behind a long
one *waited*, it was not slow.

Nothing internal reaches the user. There is no queue depth, no worker name and
no thread state in any of these strings. A wait under a second is not reported
as a number at all, because "a moment" is truer and more useful than "0.4 s".

### Precedence

The job ledger and the file on disk are combined in a fixed order:

1. An **in-flight** job wins over anything on disk, so a session being
   re-analyzed shows that, rather than showing a stale result as current.
2. Otherwise a **readable** analysis wins. A job that failed after a previous
   analysis succeeded leaves the previous one intact and current — which is
   exactly what the atomic write guarantees — and the failure is still reported
   alongside it.
3. Otherwise a **failed** job explains the absence.

### Bounds

The ledger remembers in-flight jobs (bounded by the queue) plus
`JOB_LEDGER_CAPACITY` = 64 finished ones, evicting oldest-finished first. An
in-flight record is never evicted: losing one would make a running analysis look
as though it had never been requested.

A request refused because the queue was full is recorded as a *failure with a
reason*, not erased. A session that silently never gets analyzed is precisely
what the ledger prevents.

**Recorder completion remains independent of analyzer completion.** The
completion hook fires only after the frame stream is closed and the manifest is
final, and it does one bounded `try_send`. A session records identically whether
or not analysis ever runs.

## 4. Re-analysis

A recovery affordance, not a driving control.

### What it may touch

| File | Treatment |
| --- | --- |
| `frames.rlframes` | never written |
| `manifest.json` | never written |
| `analysis.json` | replaced atomically (temp file, `sync_all`, rename) |

A failed re-analysis therefore leaves any previous analysis exactly where it
was. An `analysis.json` written by an unsupported schema can be regenerated from
the persisted canonical frame stream, which is the whole reason that stream is
kept.

### When it is offered

Only where the automatic path has already been tried and did not produce a
readable result — a `failed` analysis, or an `unsupported_schema` one — and only
for a session with safely readable frames. It is never offered while a job is in
flight, and never as part of a normal drive.

The Sessions view exposes it as a single `Re-run analysis` button inside the
analysis banner, rendered only when `banner.offerReanalysis && banner.problem`.
That gating is asserted by a test, because it is the entire difference between a
recovery path and a control a driver is invited to press after every lap.

It uses the same bounded queue as every other job, refuses a session without
readable coverage, and refuses a session already queued.

## 5. Threads

| Thread | Owns | Can it block ingestion? |
| --- | --- | --- |
| UDP ingress | socket reads | — |
| `telemetry-publisher` | 4 Hz counter publication | no |
| `session-recorder-writer` | all recording disk I/O | no (bounded drop-newest queue) |
| `session-analysis` | analysis jobs | no (bounded `try_send`) |
| `session-recovery` | frame-stream scans | no (one-slot wakeup) |
| `session-retention` | directory sweeps and deletions | no (one-slot wakeup) |

Shutdown order, from `lib.rs`: publisher, listener, capture, recorder, analyzer,
recovery, retention. Housekeeping is stopped after the work it observes, and
neither can hold exit open — a recovery scan stops between records and a
retention sweep stops between sessions.
