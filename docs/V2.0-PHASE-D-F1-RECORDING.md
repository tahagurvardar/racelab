# V2.0 Phase D — F1 25 recording

Phase D implements local F1 25 recording and factual session history alongside
Forza Horizon 6. It keeps each game's listener, adapter, recorder and storage
format separate. There is no F1 driving analysis, cloud service or AI feature.
For v2.0.0 stable, the existing F1 release gate is enabled after live-game
acceptance passed, as confirmed by the release owner on 2026-10-04. Automated
fixtures provide regression evidence separately from that manual acceptance.

## Identity and lifecycle

A recording belongs to one nonzero F1 `sessionUID` and one valid
`playerCarIndex`. RaceLab generates its own directory/session ID separately.
The game UID is serialized as a decimal string to preserve its 64-bit value
across JavaScript. Packets and events from another UID cannot enter the session.

Recording starts after the following conditions hold continuously for one second:

- F1 support is enabled and the UID/player index are valid.
- A matching Session packet is no more than five seconds old, describes a
  nonzero session type, and does not report spectating.
- Matching player Car Telemetry or Lap Data is no more than one second old.
- The UID has not already ended and has not been refused by recorder ownership.

Recording does not require the car to move. A garage/menu that continues sending
valid session/player data can remain part of the same recording. `SSTA` is
recorded as an event, rather than being the sole start trigger.

UID or player-car changes finalize immediately. `SEND` or Final Classification
starts a five-second settlement window so final Session History can arrive.
Chequered Flag is retained as an end signal but does not alone finalize.
Silence over three seconds enters grace; reaching 60 seconds without accepted
telemetry finalizes as `telemetry_lost`. Resuming in grace keeps the recording
and counts a telemetry gap. RaceLab shutdown finalizes as interrupted with
`racelab_shutdown`; write errors also produce interrupted sessions and surfaced
error status. Ordinary UID/player changes, game end and telemetry loss use the
normal completion policy. Timings are defaults implemented in code, still
awaiting manual validation in the game.

## Sampling and persistence

The recorder runs on a dedicated background thread. Every 100 ms (10 Hz), it
copies the aggregator's latest held packets and new events under a short lock.
Decoding and disk work then run outside the UDP receive path and UI thread.
This is latest-value sampling, not a native-rate packet archive. Each player
family contributes only when its overall frame identifier is newer than the
last sampled identifier. Missing families remain absent; idle ticks do not
duplicate old readings. Damage contributes at most once per second. Late
ticks, gaps, out-of-order drops and event loss/caps are counted.

F1 directories live under the same sessions root and storage budget as FH6:

| File           | Implemented contents                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------- |
| `session.json` | Multi-game envelope, F1 identity/context, family coverage, integrity and recovery                 |
| `samples.rlf1` | Versioned, length-prefixed MessagePack player samples with sequence/monotonic time and end marker |
| `events.jsonl` | Append-only event code and detail bytes, decoded when read                                        |
| `laps.json`    | Completed/provisional laps, best references and lap positions                                     |
| `tyres.json`   | Stints, latest tyre sets and bounded fitted changes                                               |
| `result.json`  | Player Final Classification, only when received                                                   |

Coded values are stored as raw numbers and labeled on read. Context includes
start/latest Session facts, bounded weather forecast, minimal player participant
facts and Time Trial references when present. There are no raw datagram dumps in
session storage. Sample/event streams are flushed at five-second checkpoints;
metadata/side files use atomic writes. Finalization closes/syncs streams, writes
side files and metadata, releases ownership and then signals housekeeping.
Write failures remain visible; no claim of a successful recording replaces them.

## Lap authority, events and other families

Session History is authoritative for completed laps, sector times, validity
bits and best-lap/best-sector references. Lap Data rollover can create a
provisional lap only while History has not described it; it never replaces an
authoritative record. Lap Positions enrich start/end position facts. The UI
names provisional records explicitly and derives best-lap display from History.

Events retain their session time, sequence, code and detail bytes. Decoded
details and player/car references are attached on read. Button-status events
are ignored and counted. Defaults cap stored events at 20,000 and pending
start-window events at 64; aggregator misses and over-cap events are reported.
Detail reads return at most 2,000 events and state how many were omitted. The
UI pages long lap/event tables rather than rendering an unbounded history.

Tyre stints come from Session History and classification; the latest Tyre Sets
snapshot and fitted changes are retained, with at most 64 fitted changes.
Damage stores player facts only. Final Classification retains the player's
position, grid, laps, points, race time, penalties and stints. Time Trial's
session-best, personal-best ghost and rival ghost remain separate references;
ghost facts never become player telemetry, laps or race classification.

The Phase D decoder additions cover packet IDs 1, 3, 4, 8, 10, 11, 12, 14 and
15, supplementing existing player families 2, 6, 7 and 13. Unsupported codes
remain raw codes; unavailable values remain unavailable.

## Recovery, retention and ownership

Startup reclassifies leftover F1 recordings as interrupted and marks recovery
pending. Background scans count readable samples/events and inspect side files.
A partial last sample or event line does not erase readable earlier records.
Recovery reports complete, truncated, damaged or unreadable outcomes; it never
turns an interrupted session into a normal completed session or invents laps.

FH6 and F1 share the existing oldest-first retention budget (8 GiB default).
Whole identifiable sessions are deleted until under budget; active recordings,
pending/running jobs and unidentifiable directories are protected. Protection
is checked at deletion time. Rename-before-delete avoids exposing a partially
deleted session, and deletion counts/failures remain reportable.

The first recorder to claim the single recording slot keeps it until
finalization. The other game's attempted session is refused and counted; it
does not silently begin recording the remainder when the slot becomes free.
Its next session may claim ownership. Switching the active Live game cannot
change this ownership. REC names the recorder: `REC · Forza Horizon 6` or
`REC · F1 25`; without an owner it says `Not recording`.

## Sessions and setup

The history list combines FH6 and F1 sessions, labels each game, sorts newest
first with a session-ID tie break, and offers All games / Forza Horizon 6 /
F1 25 filters. A hidden selection moves to the newest visible row. A filter
with no rows clears detail and invalidates outstanding reads.

F1 detail has Summary, Laps, Events and Data. Selecting F1 opens no FH6 analysis
polling lane. The header and Data status show Recording only when the F1 recorder
owns that session; a leftover recording file shows Not finalized. Selecting
FH6 retains its existing analysis behavior. Generation
and request-sequence checks reject obsolete replies and mismatched session IDs.
The shell owns one F1 recorder polling loop at 500 ms; Sessions reads store
slices. Only the recording row follows duration ticks. The first F1 completion,
including an interrupted finalization, refreshes history even when no earlier
completed ID existed.

First-run copy names both supported games and says only the game played is
needed. It retains the existing layout and completed V1.1 setup behavior.

## Privacy and release gate

Session storage excludes participant names and network IDs. Only active-car
count and the player's team, race number, AI flag and My Team flag are kept
from Participants. Opponent references in events are car indices, not identities.
Samples, damage, classification and motion are player-only.

For v2.0.0 stable, `F1_ENABLED_IN_RELEASE` is `true` in `f1_evidence.rs` after
live-game acceptance passed. Both debug and release builds enable F1 by default.
The existing `RACELAB_F1_EVIDENCE=0`/`false` explicit disable remains supported.
The same gate governs listener, Live and recording. Development fixture capture
still requires `RACELAB_F1_CAPTURE` and a debug build; it does not ship enabled
and is separate from normal session persistence.

## Evidence and manual acceptance

Real fixtures in `src-tauri/tests/fixtures/f1_25/` are four captured Time Trial
snapshots: stationary, driving, braking and high speed, each holding IDs 2, 6,
7 and 13. Their manifest records sizes/hashes and UID redaction; decoded Live
snapshots are pinned to Rust decoder output. These are evidence for those
player families, not a captured Phase D race lifecycle.

Phase D packet binaries under the separate `synthetic/` directory come from
independent specification writers. Recorder/recovery/retention/ownership stress
tests use synthetic packets and clocks with real files. Review F1 session data
in `review/f1-session-fixtures.ts` is deterministic synthetic UI data. F1 Live
review values still come from the real captured player snapshots.

Review URLs use `/review/shell.html` with `sessions=multi-game`, `f1-empty` or
`f1-long`. `scenario=f1-recording` exercises F1 REC and the recording row;
`scenario=fh6-recording-f1-live` exercises FH6 ownership with F1 Live visible.
Select the F1 row to review each detail tab. Existing FH6 review scenarios remain.

The original Phase D manual acceptance checklist covered real start/end timing, garages/menus,
pause/resume and disconnection, session/car changes, race/practice/qualifying/
Time Trial, final History after classification, real tyres/damage/events, crash
recovery and two-game ownership. The release owner confirmed F1 25 live-game
acceptance passed on 2026-10-04. Automated finalization checks remain regression
evidence; they do not substitute for that manual acceptance.
