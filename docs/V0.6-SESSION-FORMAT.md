# V0.6 — Persistent session format

RaceLab V0.6 stores **normalized `TelemetryFrame` records**, never raw game
datagrams. Raw UDP capture (V0.3, `.rlcap`) is unchanged and remains a
diagnostics-only feature with its own format, documented in
[RAW-CAPTURE-FORMAT.md](RAW-CAPTURE-FORMAT.md).

## Storage location

```text
%LOCALAPPDATA%\com.tahagurvardar.racelab\sessions\
  <session-id>\
    manifest.json      human readable, versioned session metadata
    frames.rlframes    versioned, streamable, binary normalized frame stream
    manifest.json.tmp  transient; only exists during an atomic manifest write
```

`<session-id>` is the existing `SessionEngine` identifier
(`<128-bit app instance>-<counter>`). The recorder never invents its own ID.
Identifiers are validated against `[A-Za-z0-9_-]{1,128}` before they are used as
a directory name, so a foreign identifier can never escape the sessions root.

## `frames.rlframes` — RLFRAMES v1

Little-endian throughout. The container is hand-framed; each record's payload is
**named MessagePack** produced by `rmp-serde`.

> **Since V0.8:** the container framing above is unchanged and
> `frame_format_version` is still 1, but the canonical frame payload it carries
> is separately versioned and is now **2**. This build writes schema 2 and reads
> schemas 1 and 2; a schema-1 record is decoded through a frozen compatibility
> struct and converted, and no existing recording is ever rewritten. See
> [V0.8 schema](V0.8-TELEMETRY-SCHEMA.md).

```text
Header (once)
  magic                              8 bytes  "RLFRM\r\n\0"
  frame_format_version               u32      1
  telemetry_frame_schema_version     u32      1 or 2 (see below)
  session_id_len                     u32      1..=128
  started_at_unix_ms                 u64
  session_id                         session_id_len bytes, UTF-8

Frame record (repeated, append-friendly)
  tag                                u8       1
  payload_len                        u32      <= 1 MiB
  payload                            payload_len bytes, MessagePack map

Footer (once, only on a clean finalize)
  tag                                u8       2
  frame_count                        u64
  duration_us                        u64
  recorder_dropped_frames            u64
```

### Record payload

The MessagePack map has exactly three keys, in this order:

| Key | Type | Meaning |
|---|---|---|
| `sequence` | u64 | `TelemetryHub` publication sequence; strictly increasing |
| `monotonic_ms` | u64 | Capture monotonic milliseconds — the authoritative timing source |
| `frame` | map | The canonical `TelemetryFrame`, verbatim |

`frame` carries every canonical field: `active`, `game`, `vehicle_id`,
`game_timestamp_ms`, `engine` (rpm / idle / max), `acceleration`, `velocity`,
`angular_velocity`, `orientation`, `position`, `speed_mps`, `controls`
(throttle, brake, clutch, handbrake, steering), `gear`, and `sourceSpecific`.
For FH6, `sourceSpecific.fh6` is where the wheel/tire temperatures, lap and race
data, raw gear code, dash extensions and unknown byte regions live — the V0.5
canonical contract puts them there, and V0.6 stores them unchanged. When a
future adapter adds canonical wheel/suspension fields to `TelemetryFrame`, named
MessagePack records them without any change to this container.

### Guarantees

- **Lossless.** `f32` stays `f32`; `u64` stays `u64`. Decoding a record yields a
  `TelemetryFrame` that compares equal to the published one.
- **Null stays null.** `Option::None` encodes as MessagePack `nil` and decodes
  back to `None`. An unavailable value is never stored as `0`, and a genuine
  `0.0` is never stored as null.
- **Deterministic.** Struct fields encode in declaration order; the
  `serde_json::Value` inside `sourceSpecific` uses an ordered map, so the same
  frame always produces the same bytes.
- **Streamable and bounded.** The reader holds one record at a time and rejects
  any record claiming more than 1 MiB. It is not one giant JSON array, not raw
  UDP, and not hex text.
- **Crash-tolerant.** The footer is optional on read. A stream that ends without
  one is decoded up to its last whole record and reports `end == None`. A
  partial trailing record is a clean end of stream, not corruption of the file.

The reader (`session_format::FrameStreamReader`, `read_all_frames`) is internal:
it exists for tests and future offline analysis. **No Tauri command exposes the
frame stream**, so the frontend can never request a full session's frames.

## `manifest.json` — SessionManifestV1

Pretty-printed JSON, written with a temp file plus rename so a reader sees
either the previous manifest or the new one — never a half-written file, and
never an unfinished session claiming `completed`.

| Field | Notes |
|---|---|
| `schema_version` | `1` |
| `session_id` | The `SessionEngine` ID |
| `status` | `recording` \| `completed` \| `interrupted` |
| `game`, `protocol`, `vehicle_id` | From the session; `null` when unknown |
| `started_at_unix_ms`, `ended_at_unix_ms` | End derived from start + monotonic duration |
| `duration_us` | `SessionEngine` monotonic duration, including grace |
| `frame_count`, `active_frame_count`, `inactive_frame_count` | Frames actually written |
| `recorder_dropped_frames` | Queue overflow for this session |
| `completion_reason` | e.g. `grace_expired`, `listener_stopped`, `vehicle_or_game_changed` |
| `frame_file` | `frames.rlframes` |
| `frame_format_version`, `telemetry_frame_schema_version` | As stored in the stream header |
| `summary` | `SessionSummaryV1`, or `null` while recording and for interrupted sessions |
| `created_by_racelab_version` | Crate version that wrote the session |

While recording, the manifest is rewritten on a 5-second **elapsed-time**
cadence, after flushing the frame file, so a checkpointed count never exceeds
what is durable on disk. The writer tracks its own checkpoint deadline and
re-evaluates it after every command it handles; it does **not** rely on an idle
receive. That distinction matters: under continuous 60-75 Hz telemetry a frame
arrives every ~13-17 ms, so a receive timeout would be reset forever and
checkpoints would never fire during exactly the sessions they exist for. A
checkpoint refreshes `frame_count`, `active_frame_count`,
`inactive_frame_count`, `duration_us`, `recorder_dropped_frames` and any
game/vehicle identity learned from the stream. It never writes a summary and
never changes `status`, which stays `recording`.

### Crash safety

- Recording in progress → `status: recording`.
- Clean completion → frame file flushed, footer written, `sync_all`, summary
  calculated, manifest atomically replaced with `status: completed`.
- On startup, every session still marked `recording` is reclassified as
  `interrupted` with `completion_reason: interrupted_racelab_did_not_finalize`
  and `summary: null`. It is **never** marked completed, and never gains a
  summary. Its `frame_count` is the last checkpoint, which is approximate.
- A writer failure mid-session finalizes as `interrupted` with
  `completion_reason: recorder_write_error`.

## `SessionSummaryV1` — RaceLab V0.6 definitions

Computed incrementally on the writer thread from one previous sample; the
session is never held in memory.

| Field | Definition |
|---|---|
| `duration_seconds` | `SessionEngine` duration, including grace |
| `measured_seconds` | Sum of accepted inter-frame gaps. **Not** the percentage denominator |
| `frame_count` | Frames written |
| `max_speed_kmh`, `max_rpm` | Maximum over samples where the value exists |
| `average_speed_kmh`, `average_rpm` | **Time-weighted**, never a naive sample mean |
| `full_throttle_seconds` | Time with normalized throttle **≥ 0.95** |
| `full_throttle_percent` | Of the time **throttle itself** was available, not of `measured_seconds` |
| `braking_seconds` | Time with normalized brake **> 0.05** |
| `braking_percent` | Of the time **brake itself** was available, not of `measured_seconds` |
| `gear_change_count` | Transitions of **canonical** `Gear`; `null` when no adapter supplies one |
| `distance_meters` | Speed integrated over monotonic time; `null` unless speed covers ≥ 99% of measured time |
| `data_quality` | `recorder_dropped_frames`, `complete`, `excluded_gaps` |

**Time weighting.** For consecutive frames at `t[i-1]` and `t[i]`, the interval
`dt = t[i] - t[i-1]` is attributed to the values of the *earlier* sample
(left-hand weighting). This is the only interpretation available without
inventing interpolation between telemetry samples. An average is
`Σ(value × dt) / Σ dt` over intervals where that channel was available, so a
channel that is only sometimes present never distorts the denominator.

**Percentage denominators.** Every percentage divides by the time its own
channel was available, never by `measured_seconds`. `full_throttle_percent` is
full-throttle time over the time throttle was reported; `braking_percent` is
braking time over the time brake was reported. Because each numerator only ever
accumulates intervals that its own denominator also accumulates, a percentage
can never exceed 100%, and a channel that is reported for only part of a session
is measured against its own availability rather than being diluted by the rest
of the session. A percentage is `null` when its channel was never available.

**Gap exclusion.** An interval longer than `MAX_SAMPLE_GAP_MS = 1000` is a
telemetry gap, not measured driving. It is excluded from every time-weighted
statistic and counted in `data_quality.excluded_gaps`, so a pause or a burst of
recorder drops cannot silently inflate a duration or a distance.

**Gear changes today.** FH6's canonical `gear` is `null` by the V0.5 contract —
the raw gear code's semantics have not been independently validated, and the raw
code lives in `sourceSpecific`, which is game-specific. V0.6 therefore reports
`gear_change_count: null` for FH6 rather than counting a value it cannot defend.
The counter is implemented and tested; it will start producing numbers as soon
as an adapter supplies canonical gears.

**Distance today.** `TelemetryFrame` has no validated canonical distance field.
FH6's `distance_traveled` is source-specific and unvalidated, so V0.6 integrates
canonical speed over monotonic time instead, and reports `null` when speed does
not cover the session. This is an estimate from speed, not a game odometer.

**`complete`** is true only when `recorder_dropped_frames == 0` and the writer
reported no error.

## Writer architecture

```text
TelemetryHub.publish  (ingestion thread, hub lock already released)
        |  try_send, never blocks, never touches disk
        v
bounded recorder queue — 4096 frame slots + 64 reserved lifecycle slots
        |
        v
session-recorder-writer thread
        |  MessagePack encode, BufWriter, manifest checkpoints
        v
frames.rlframes + manifest.json
```

- **Queue capacity: 4096 frames.** At 75 Hz that is roughly 55 seconds of
  buffered telemetry — far beyond any plausible disk stall — while bounding
  queue memory to a few MiB.
- Frame admission is gated on a frame-only counter, so a saturated frame queue
  can never starve a session start or completion out of the channel. Lifecycle
  commands use the 64 reserved slots.
- Overflow **drops the newest frame** and increments the drop counters.
  Pressure is never relieved by growing the queue. Two counters exist and mean
  different things: `RecorderStatus.recorder_dropped_frames` is scoped to the
  **current** recording and is reset to zero when a session starts, so a lossy
  session never leaves a later clean session looking lossy — this is the one the
  user-facing loss warning reads. `RecorderStatus.lifetime_dropped_frames` is a
  process-lifetime diagnostic total and never drives that warning. The session
  manifest's `recorder_dropped_frames` and `summary.data_quality` are per-session
  and are derived by difference from the lifetime total, which stays correct even
  when a completion is finalized after the next session has already started.
- No disk I/O, no `fsync`, no manifest write and no directory creation happens
  on the ingestion path. The writer thread creates the session directory too.
- The recorder's admission mutex guards bounded in-memory hand-off only; it is
  never held across disk I/O, and the `TelemetryHub` mutex is already released
  before the recorder is called at all.
