# V2.0 Phase A — F1 25 UDP evidence adapter

Phase A receives and classifies F1 25 UDP traffic and nothing else. It reads
the 29-byte common header and the datagram length. It does not read a single
payload byte, build a `TelemetryFrame`, record a session or run analysis.
FH6 code paths, persisted formats and the V1.1 version are unchanged.

## Protocol authority

"Data Output from F1 25 Game" v3 (EA, 2025), from the official EA forum
"F1 25 UDP Specification" post. Relevant statements:

- All values are little endian. All structures are packed, with no padding.
- `PacketHeader` (29 bytes): `uint16 packetFormat` (2025), `uint8 gameYear`
  (25), `uint8 gameMajorVersion`, `uint8 gameMinorVersion`,
  `uint8 packetVersion` ("all start from 1"), `uint8 packetId`,
  `uint64 sessionUID`, `float sessionTime`, `uint32 frameIdentifier`,
  `uint32 overallFrameIdentifier`, `uint8 playerCarIndex`,
  `uint8 secondaryPlayerCarIndex` (255 if none).
- F1 25 can also emit UDP Format 2024 and 2023. Phase A rejects both as
  `wrong_packet_format`; it does not reinterpret them.

EA has since published a separate "F1 25: 2026 Season Pack" specification.
Phase A has not been checked against it. If that update changes any
`packetVersion` or size, Phase A reports it as `unsupported_packet_version` or
`size_mismatch`. It never guesses.

## Classification order

The first check that fails is the one reported:

1. `truncated`: fewer than 29 bytes.
2. `wrong_packet_format`: not 2025.
3. `wrong_game_year`: not 25.
4. `unknown_packet_id`: above 15.
5. `unsupported_packet_version`: not 1.
6. `size_mismatch`: not the exact spec size for that ID.

Only an accepted packet updates the "current" header, the detection clock and
the rates. A rejected datagram is counted and nothing more.

## Runtime

- A second `ingress::Listener` on `127.0.0.1:20777`, loopback only, so there
  is no firewall prompt. It shares no socket, sink, hub, recorder or capture
  with FH6. It binds after FH6 in the background publisher thread, and a bind
  failure is logged and shown in Diagnostics without stopping FH6.
- It is enabled by default in debug builds and disabled in release builds.
  `RACELAB_F1_EVIDENCE=1|0|true|false` overrides that; any other value is a
  startup error. A release build therefore does not take 20777 away from an
  F1 tool the user already runs.
- Evidence is bounded: sixteen fixed per-ID slots plus scalar counters, all
  saturating. Diagnostics receives a fixed document of about 5 KiB with no
  payload bytes and no hex preview. `sessionUID` is sent as a decimal string,
  because a JavaScript number cannot hold a full `uint64`.
- "Detected" means an accepted packet arrived within the last 2 s.
- `get_f1_evidence` is read at 1 Hz by the shell-level `useF1Evidence` hook.
  Diagnostics gets an "F1 25" tab only when the backend reports the listener
  enabled. Once the backend says the listener is disabled or absent, the hook
  stops calling it.

## Manual acceptance (pending)

1. Close any other program bound to UDP 20777. Check with
   `netstat -ano -p udp | findstr 20777`. On Windows, a loopback bind and a
   wildcard bind on the same port can coexist, and then only one of them
   receives the datagrams.
2. Run `pnpm tauri dev`. The log should contain
   `F1 25 evidence listener bound to port 20777`.
3. In F1 25, set UDP Telemetry On, Broadcast Off, IP 127.0.0.1, Port 20777,
   Rate 20 Hz, UDP Format 2025.
4. Enter Time Trial and drive for 1–2 minutes.
5. Diagnostics → F1 25 should show "F1 25 detected", `packetFormat` 2025,
   `gameYear` 25, a stable `sessionUID` and the expected `playerCarIndex`.
   Rates should be about 20 Hz for 0/2/6/7/13, 2 Hz for 1/5, 10 Hz for 10,
   and 1 Hz for 14/15. The rejected and size-mismatch counters should stay at
   0. Record whether IDs 4, 14 and 15 now appear. If they do, they move from
   `spec_only` to live.
6. Confirm there is no firewall prompt.
7. With F1 still running, start FH6 Data Out to 127.0.0.1:20440 and confirm
   FH6 detection, Live and recording behave exactly as in V1.1.
