# V0.6 — Automatic session recorder

2026-09-19. V0.6 adds automatic, normalized session recording on top of the
manually validated V0.5.1 lifecycle. **No manual Forza Horizon 6 validation of
V0.6 has been performed**; the required steps are listed at the end of this
report. The format itself is specified in
[V0.6-SESSION-FORMAT.md](V0.6-SESSION-FORMAT.md).

## What did not change

- `src-tauri/src/ingress.rs` and `src-tauri/src/packet.rs` are byte-identical to
  Git HEAD. The frozen UDP ingress was not touched, and no blocker requiring a
  change was found.
- `capture.rs` / `capture_format.rs` are unchanged. V0.3 raw datagram capture
  keeps its own `.rlcap` format and is now collapsed under a diagnostics
  disclosure in the UI.
- `SessionEngine` remains authoritative for session identity, state and
  duration. No state, threshold, grace rule or ID scheme changed. The only edit
  is additive: the engine now records the transitions it already performs into a
  drained event list, so persistence can observe them.
- FH6 packet classification (`valid active` / `valid inactive` / `invalid FH6` /
  `unknown protocol`), detection, health and the canonical `TelemetryFrame`
  field semantics are unchanged. `telemetry.rs` gained `Deserialize` derives
  only; serialization output is identical.

## Lifecycle mapping

| `SessionEngine` transition | Recorder action |
|---|---|
| New session created (first locked active frame) | Open admission with **that** session ID; writer creates `sessions/<id>/`, the frame stream and a `recording` manifest |
| Frame published while session is `ACTIVE` or `GRACE` | Enqueue; writer appends one record |
| `ACTIVE` → `GRACE` | Nothing. Same writer, same file, same manifest, no finalize |
| `GRACE` → `ACTIVE` | Nothing. The same writer continues |
| `finish(...)` — grace expiry, vehicle/game change, listener stop/restart, transport error | Close admission, drain the queue, flush, write the footer, `sync_all`, calculate the summary, atomically replace the manifest with `completed` |
| Next session starts | New ID, new directory, new writer. Never a recorder-invented ID |
| Process killed without finalize | Manifest stays `recording`; the next startup reclassifies it as `interrupted` with no summary |

The user presses nothing. There is no Start Recording command in the backend and
no such control in the UI; the frontend structural test asserts that no button
in the sessions panel controls recording.

## Storage, encoding and queue

- Path: `%LOCALAPPDATA%\com.tahagurvardar.racelab\sessions\<session-id>\`
- `manifest.json` — `SessionManifestV1`, pretty JSON, temp file + rename.
- `frames.rlframes` — RLFRAMES v1: fixed binary header, then length-prefixed
  **named MessagePack** records, then an optional footer. Streamable, compact,
  deterministic, lossless, and readable up to the last whole record after a
  crash. Not a JSON array, not raw UDP, not hex text.
- Queue: **4096 frame slots plus 64 reserved lifecycle slots**, `try_send`,
  drop-newest, counted as `recorder_dropped_frames`. Frame admission is gated on
  a frame-only counter so a full frame queue cannot starve a session start or
  completion. Nothing on the ingestion path touches disk, and the
  `TelemetryHub` mutex is released before the recorder is called.

## Summary definitions (RaceLab V0.6)

- Full throttle: normalized throttle **≥ 0.95**.
- Braking: normalized brake **> 0.05**.
- Averages are **time-weighted** over monotonic frame timing, using left-hand
  weighting: the interval between two frames is attributed to the earlier
  sample's values. Percentages use the time that channel was available.
- Inter-frame gaps longer than **1000 ms** are excluded from time-weighted
  statistics and counted in `data_quality.excluded_gaps`.
- `gear_change_count` is `null` for FH6: canonical `Gear` is null by the V0.5
  contract, and the raw FH6 gear code is source-specific and unvalidated. The
  counter is implemented and tested but will not produce a number until an
  adapter supplies canonical gears. This is deliberate — a count derived from an
  unvalidated code would be a fabricated statistic.
- `distance_meters` integrates canonical speed over monotonic time and is `null`
  unless speed covers at least 99% of the measured interval time. There is no
  validated canonical distance field to trust instead.

## Remaining risks

- **No live-game validation yet.** Every result above is synthetic or
  fixture-derived. FH6 behaviour in menus, loading, fast travel and photo mode
  under recording has not been observed.
- Disk growth is unbounded over time: V0.6 has no retention policy, and a
  three-minute FH6 session is on the order of 10 MB because the FH6
  source-specific envelope is stored in full. Deletion is a manual file
  operation today.
- `gear_change_count` and `distance_meters` are `null` for FH6 by design. Anyone
  expecting numbers there will see `—`.
- Interrupted sessions report their last elapsed-time (5-second) checkpoint's frame count, not
  an exact one, and carry no summary.
- A recorded session is a faithful copy of what the hub published. It cannot
  prove nothing was lost on the wire before reception; UDP loss remains
  invisible, as in every earlier phase.
- The startup interrupted-session sweep reads every session manifest
  synchronously during Tauri setup. With thousands of sessions this would add
  startup latency; listing is separately capped at 2000 directories.
- `list_recent_sessions` reads manifests on every call rather than caching them.

## Manual FH6 verification steps

Perform these with the game; do not treat the automated results above as a
substitute.

1. Launch RaceLab. The recorder panel shows **Idle · waiting for an active
   session** and the sessions directory path. Recent Sessions may be empty.
2. Launch Forza Horizon 6 with data-out to `127.0.0.1:20440`.
3. Start driving. Confirm: connection reaches `SESSION_ACTIVE`, the recorder
   panel switches to **Recording**, the session ID shown there is identical to
   the session ID in the live telemetry panel, and frames written climbs at
   roughly the valid-frame Hz.
4. Drive 2–3 minutes. Confirm **Recorder drops = 0** and queued frames stays
   near zero. Confirm hub subscriber drops and receive errors stay 0.
5. Open a short menu (a few seconds) and return to driving. Confirm the session
   ID does **not** change, the recorder stays **Recording**, frames written keeps
   increasing, and no second row appears in Recent Sessions.
6. Open a long menu and wait out the grace period (default 10 s). Confirm the
   session completes, the recorder returns to idle, and one new row appears in
   Recent Sessions with status **Completed**.
7. Resume driving. Confirm a **new** session ID, a **new** directory under
   `%LOCALAPPDATA%\com.tahagurvardar.racelab\sessions`, and eventually a second
   completed row.
8. Select the earlier session. Confirm Session Details opens immediately (no
   lag from decoding frames) and shows start/end, duration, frame count,
   recorder drops, max/average speed, max/average RPM, full-throttle and braking
   time and percent, distance if available, and data quality **Complete**.
   Gear changes will read `—`.
9. Inspect the files: `manifest.json` is readable JSON with
   `"status": "completed"` and a populated `summary`; `frames.rlframes` is
   binary and far larger.
10. Crash test (optional): kill RaceLab while recording, restart it, and confirm
    that session appears as **Interrupted · incomplete** with no summary, never
    as completed.

Report back what differs; V0.6 should not be frozen until steps 3–8 are
confirmed against the real game.
