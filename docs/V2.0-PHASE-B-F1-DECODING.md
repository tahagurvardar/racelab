# V2.0 Phase B — F1 25 typed payload decoding

Phase B decodes the player car's values from four F1 25 packets and shows
them in Diagnostics. It does not record F1 sessions, map F1 into the FH6
`TelemetryFrame` or persistence, or touch any FH6 code path.

Protocol authority: "Data Output from F1 25 Game" v3. Every struct below was
checked field by field against that document, and its byte total matches the
specification's datagram size exactly.

| ID | Packet        | Per-car struct      | Layout                                               | Size |
| -: | ------------- | ------------------- | ---------------------------------------------------- | ---: |
|  6 | Car Telemetry | `CarTelemetryData`  | 29 + 22 × 60 + 3 (MFD, MFD secondary, suggested gear) | 1352 |
|  7 | Car Status    | `CarStatusData`     | 29 + 22 × 55                                         | 1239 |
|  2 | Lap Data      | `LapData`           | 29 + 22 × 57 + 2 (TT PB car, TT rival car)           | 1285 |
| 13 | Motion Ex     | — (player car only) | 29 + 61 × float                                      |  273 |

## Rules the decoders follow

- **They decode only accepted packets.** A decoder runs only on a datagram
  the Phase A classifier accepts as exactly its packet type. Anything else
  is a `DecodeError`, never a guess.
- **Player selection.** `playerCarIndex < 22` selects the slot. Any other
  value, including 255 when spectating, makes `player` absent for every
  family. Index 0 is never assumed. Packet-level fields (MFD panel,
  suggested gear, Time Trial car indices) are still decoded.
  `secondaryPlayerCarIndex` is not used.
- **Motion Ex** has no per-car array. It is still reported as unavailable
  when `playerCarIndex` is invalid, because the specification does not say
  whose car it describes in that state. That is a policy choice, not a spec
  statement.
- **Wheel order.** The specification says all wheel arrays are RL, RR, FL,
  FR. Decoders turn them into named corners (`Wheels { rear_left, ... }`)
  at the point of reading. FH6's order and types are not reused.
- **Units** are the specification's, and appear in field names only where
  the specification states one (for example `speed_kmh`, `tyres_pressure_psi`,
  `ers_store_energy_j`). Fields the specification gives no unit for (fuel
  mass, wheel speed, suspension position, forces, aero heights, roll angles)
  carry none. Nothing is converted.
- **Codes** keep their raw value: `{ raw, label }`. A value the
  specification does not name is `Unknown(raw)` with a null label. Fields
  documented only as "whether …", with no stated meaning per value
  (`m_networkPaused`, `m_pitStopShouldServePen`), stay raw integers.
  `m_speedTrapFastestLap` stays raw, with 255 meaning "not set" as
  documented.
- **Split times** (sectors, deltas) keep both wire parts and add
  `total_ms = minutes × 60000 + ms`, which is exact integer arithmetic.
- **Values are verbatim.** Negative lap distance before the line, negative
  fuel laps and implausible values are reported as sent. Nothing is
  clamped, smoothed or "corrected".

## Known upstream report: LapData field order

A community post in EA's F1 25 UDP specification discussion reports that
`m_driverStatus` and `m_gridPosition` appear swapped relative to the
specification. The poster saw grid position 0 for all drivers at race start.
EA has not confirmed it as far as RaceLab has found, and the thread could not
be read directly (HTTP 403).

**RaceLab decodes in specification order and does not swap anything on a
report.**

**Result from the real fixtures (2026-10-03, game 1.26, Time Trial, player
car):** decoded in specification order, `driver_status` is "in garage" (0)
while parked and "flying lap" (1) in all three driving snapshots, and
`grid_position` is 0 throughout. Swapped, the bytes would read "in garage"
at 170 km/h. **Specification order is confirmed for this case.** Race-start
grid positions, which is where the report came from, remain untested. See
`src-tauri/tests/fixtures/f1_25/README.md` for the full fixture review.

## Aggregation (`f1_live`)

- One fixed slot per family (Car Telemetry, Car Status, Lap Data, Motion
  Ex) holds that family's latest accepted datagram, at most 1352 bytes.
  There is no history and no allocation on the receive thread. Decoding
  happens when Diagnostics reads the snapshot, at 4 Hz.
- Each family reports its own `frame_identifier`,
  `overall_frame_identifier`, `session_time` and `age_ms`. They are never
  presented as one frame.
- **Out of order.** A datagram whose `overallFrameIdentifier` is lower than
  the one already held for its family is dropped and counted. The
  specification says that identifier "doesn't go back after flashbacks", so
  a flashback, which rewinds `frameIdentifier`, is still accepted.
- **Session change.** A new `sessionUID` in any accepted packet clears
  every slot (counted as `session_resets`).
- **Player change.** A new `playerCarIndex` within the session clears every
  slot (counted as `player_resets`). All four families are player data.
- **Accepted transient.** A late straggler from a previous session is
  indistinguishable from a new session and clears the slots once.

## Development fixture capture

Disabled unless `RACELAB_F1_CAPTURE=1` **and** a debug build. In a release
build the variable is ignored and logged.

- A capture writes one snapshot only when explicitly requested: the four
  held packets, each at most 1 s old and all from the same session and
  player, plus `manifest.json`. Files go to a staging directory that is
  renamed into place.
- Bounds: 16 snapshots per run and 64 snapshot directories in total. The
  label is restricted to `[a-z0-9-]`, and the delay to at most 15 s.
- Snapshots go to `%LOCALAPPDATA%\com.tahagurvardar.racelab\dev-f1-fixtures`,
  outside the repository. Nothing is committed automatically.
- The UI receives the manifest only, never bytes.
- `cargo run --example f1_fixture -- capture|inspect|sanitize` is the
  same path from a terminal (RaceLab must not be running for `capture`).
  `inspect` prints the decoded player values for review. `sanitize`
  replaces the sessionUID with `RACELAB!` and checks the packet still
  classifies identically.

### Capture procedure

1. Close the running dev build.
2. Start it again with capture enabled:
   `$env:RACELAB_F1_CAPTURE=1; pnpm tauri dev` (PowerShell).
3. In F1 25, enter Time Trial.
4. Open Diagnostics → F1 25 → Fixture capture.
5. Take four snapshots:
   - `stationary`: in the garage or standing still, delay "now".
   - `driving`: steady throttle, any gear.
   - `braking`: choose a 5 s or 10 s delay, then brake hard as it fires.
   - `high-speed`: flat out with DRS open if possible, delay 5 s or 10 s.
6. For each snapshot, note the HUD speed, gear and lap time, so the review
   can compare against what the game showed.

### Review procedure

The review happens before anything enters `src-tauri/tests/fixtures/f1_25/`.

1. Run `f1_fixture inspect` on every `.bin` file.
2. Compare speed, gear and RPM with the HUD notes, and check that steering
   sign, throttle and brake match the action.
3. Check the LapData `driver_status` / `grid_position` question above.
4. Run `f1_fixture sanitize` on each file into the fixtures directory.
5. Pin the reviewed values as regression tests.
