## 3. Interrupted-session recovery, on real recordings

The strongest evidence in this pass, because the input is not synthetic.

The development machine holds **13 genuinely crash-interrupted sessions**, every
one of which reports `frame_count: 0` in its manifest while holding between
0.9 MB and 43.6 MB of frames on disk. They were recorded before the manifest was
checkpointed, so the manifest never learned what the frame file contained.

## 3a. Real FH6 manual acceptance results

Observed on the machine that plays FH6, running the procedure in section 7.
These are the two results that no automated test can stand in for, because both
required the operating system and the game rather than a simulation of them.

### Windows restart during an active recording

A Windows restart was performed while a session was actively recording. This is
the harshest interruption RaceLab can face: the process is not asked to stop, it
is terminated, so the frame stream ends at whatever byte the last `write_all`
reached and the manifest holds only its last five-second checkpoint.

| Observation | Value |
| --- | --- |
| Session | `583b752113918251d10a3ba8c433d6c2-1` |
| Vehicle | `3650` |
| Manifest status after relaunch | `interrupted` |
| Recovery outcome | `truncated` |
| Readable frames recovered | **6,514** |
| `created_by_racelab_version` | `0.9.0` |
| Falsely marked `completed`? | **No** |

Every V0.10 recovery invariant held on real data:

- the session was reclassified `interrupted`, never `completed`;
- the readable prefix was recovered in full — 6,514 frames that the checkpointed
  manifest alone would not have accounted for;
- the outcome was `truncated`, which is the correct classification for a process
  killed mid-write, rather than `damaged` or `unreadable`;
- no summary was synthesized for an incomplete recording;
- `frames.rlframes` was not written.

The vehicle is `3650`, which is a **third** vehicle: the slip evidence corpus in
`docs/V0.10-EVIDENCE.md` covers `3520` and `3631` only. This recording is
therefore new evidence toward the cross-car slip question, not just an
interruption test. It does not change the V0.10 finding — three vehicles still
do not establish a portable threshold, and the semantics stay unchanged — but it
is the first addition to the corpus that question needs.

### Real retention deletion

Run with a storage budget deliberately set below current usage, after a full
backup of the sessions directory.

| Observation | Value |
| --- | --- |
| Session storage before | 1,473,378,121 bytes |
| Oldest session by start time | `6d5e2a53a6cb0b785cb6e6b2b0e3d254-1` (~16.2 MiB) |
| Session storage after | 1,456,423,353 bytes |
| Bytes reclaimed | 16,954,768 (16.17 MiB) |
| Oldest session present afterwards | **No** — `Test-Path` returned `False` |
| Next-oldest session present afterwards | **Yes** |

Both retention guarantees were confirmed on real recordings:

- **Oldest-first.** The session deleted was the oldest by start time, not an
  arbitrary one and not the largest.
- **Minimum necessary.** Deletion stopped as soon as the directory was back
  under budget. The immediately-next-oldest session survived, which is the
  observable difference between "delete until under budget" and "delete a
  batch".

The reclaimed figure matches the deleted session's size, so nothing else was
touched. A full backup was taken before the destructive step and the deleted
session was restored from it afterwards, so the evidence corpus is intact.

## 4. Long-session and backpressure results

`cargo test --manifest-path src-tauri/Cargo.toml --test session_scale -- --nocapture`

All seven pass. Figures are from the debug profile on Windows 11, which is the
pessimistic case; release is roughly 8× faster.

### Long streams

| Case | Frames | Wall | Sustained | vs 75 Hz | Dropped |
| --- | --- | --- | --- | --- | --- |
| 10 min equivalent | 45,000 | 2.39 s | 18,820 frames/s | **251×** | 0 |
| 60 min equivalent | 270,000 | 11.67 s | 23,146 frames/s | **309×** | 0 |

Release profile: 183,552 and 181,362 frames/s — **2,447×** and **2,418×**.

Publishing cost, on the thread that is the UDP ingestion thread in production:

| Case | Total in `publish` | Per frame | Exceeded one frame interval |
| --- | --- | --- | --- |
| 10 min | 191.5 ms | 4.3 µs | 0 of 45,000 |
| 60 min | 709.5 ms | 2.6 µs | 1 of 270,000 |

The single outlier is a Windows scheduler quantum, not a wait: the assertion is
on the *rate* of slow publishes rather than the maximum, because a publisher that
waited on disk would exceed a frame interval systematically rather than once in
270,000 calls.

### Memory

| Measurement | Peak working set |
| --- | --- |
| 60-minute-equivalent record + analyze, in process | **6.9 MB** |
| Analyzing the real 1,015 MB / 78-minute session | **4.8 MB** |

The second figure is the important one: a 1 GB frame stream is analyzed in 9.5 s
using 4.8 MB, producing a 66 KB `analysis.json` at 36,089 frames/s. Analyzer
memory is bounded by one record plus fixed accumulator state and is **independent
of session length**.

Queue memory is bounded by construction: `RECORDER_QUEUE_CAPACITY` = 4,096
`Arc<TelemetryFrame>` slots, and `ANALYSIS_QUEUE_CAPACITY` = 8 job slots.

### Backpressure and concurrency

| Case | Result |
| --- | --- |
| Slow disk (8-slot queue, flooded) | 1,200 written, 38,800 dropped; every frame either written or counted; no publish exceeded a frame interval; summary marked incomplete |
| Analysis while the next session records | both sessions completed, 0 drops, 0 analysis failures |
| 5 completed sessions queued | all 5 analyzed, 0 failures, 0 rejections |
| Analysis queue full | overflow refused and counted; each refusal readable as a `failed` state with a reason |
| Analyzer failure isolation | 1 failure, 2 unrelated sessions unaffected, failing session still `completed` |
| Shutdown with queued analyses | 4 sessions drained in 35 ms, nothing left in flight, no deadlock |
| Shutdown mid-recording | open session finalized `interrupted`, frames kept, no summary |

### Storage arithmetic

Measured session cost: **~3.0 KB per frame** on real FH6 recordings (1,015 MB /
339,454 frames), which is **0.81 GB per hour** at 75 Hz. The 8 GiB default budget
is therefore about ten hours of continuous recording.

The development machine's sessions directory is 1.45 GB across 45 sessions —
comfortably under the default budget, so enabling retention deletes nothing
there.

## 5. Frozen-boundary verification

Verified by `git diff --stat`: every frozen module is **untouched**.

| Frozen boundary | File | Status |
| --- | --- | --- |
| UDP ingress mechanics | `ingress.rs` | unmodified |
| Protocol packet reader | `protocol.rs`, `packet.rs` | unmodified |
| RawCapture behaviour | `capture.rs`, `capture_format.rs` | unmodified |
| SessionEngine lifecycle | `session.rs` | unmodified |
| FH6 wheel mapping / adapter | `adapters/fh6.rs` | unmodified |
| `TelemetryFrame` V2 shape | `telemetry.rs` | unmodified |
| V1 persisted compatibility | `telemetry_v1.rs` | unmodified |
| Hub, appliance, live telemetry | `telemetry_hub.rs`, `appliance.rs`, `live_telemetry.rs` | unmodified |
| Session summary | `session_summary.rs` | unmodified |
| RLFRAMES framing | `session_format.rs` | **byte format unmodified** |

Three changes touch frozen-adjacent code and are called out deliberately:

1. **`session_format.rs` — `SessionManifestV1` gains one optional field.**
   `recovery: Option<RecoveryRecordV1>`, with `#[serde(default)]`.
   `MANIFEST_SCHEMA_VERSION` stays 1 because nothing that already existed
   changed meaning: an older manifest simply has no recovery record, which is the
   correct statement about it, and serde ignores unknown fields so an older build
   reads a newer manifest unharmed. Verified by `session_compatibility` (11
   tests, unchanged and passing).

2. **`session_format.rs` — a new reader method, `next_frame_lossy`.** The RLFRAMES
   byte format, the writer and `next_frame` are all unchanged. `next_frame_lossy`
   ends the stream at an unexpected end-of-file instead of failing, and sets
   `truncated_tail`. Damage in the middle of a file still errors.

3. **`analysis_engine.rs` — the analyzer reads with `next_frame_lossy`.** Without
   this, a crashed recording's incomplete final record discards the whole
   session. The behaviour change is narrow and is asserted in both directions:
   `a_stream_that_stops_mid_record_is_analyzed_up_to_the_last_complete_frame`
   and `a_corrupt_frame_stream_fails_without_writing_an_analysis`.

Two existing tests changed as a consequence, and the reason is worth recording:
their "corrupt stream" fixtures truncated a file and appended a few junk bytes,
which at the byte level is a *longer truncated file*, not a corrupt record. They
now build genuine mid-stream damage — a record whose length prefix is honoured in
full and whose payload is a run of `0xC1`, the one byte MessagePack never
assigns — with valid records on both sides.

One further intentional change:

4. **`tests/session-state.test.mjs` — the reanalysis assertion is tightened, not
   removed.** V0.9 asserted `!/reanalyze_session/.test(panel)`. V0.10 authorises a
   recovery path, so the test now asserts that there is exactly one call site and
   that it is gated on `banner.offerReanalysis && banner.problem`. That gating is
   the entire difference between a recovery affordance and a control a driver is
   invited to press after every lap.

Unchanged and re-verified: automatic product flow (no Start Recording, no Start
Listener), no frame stream reaching React (the command surface is
`get_recorder_status`, `list_recent_sessions`, `get_session`,
`get_session_analysis`, `get_storage_status`, all manifest-scale).

## 7. Manual FH6 acceptance procedure

**This procedure was run in full and passed.** It is retained verbatim as the
repeatable gate for future releases, and as the record of what 0.10.0 was
accepted against. Section 3a holds the results of its two destructive steps.

Run in order, on the machine that plays FH6. Every step states what to observe;
a step that does not match is a failure to report, not to work around.

### Preparation

1. Confirm the app version is still `0.9.0` in `package.json`,
   `src-tauri/Cargo.toml` and `src-tauri/tauri.conf.json`. Do not bump it until
   every step below passes.
2. Note the current contents of the sessions directory, so anything retention
   removes later is a known quantity:

   ```powershell
   $s = "$env:LOCALAPPDATA\com.tahagurvardar.racelab\sessions"
   (Get-ChildItem $s -Directory).Count
   "{0:N2} GB" -f ((Get-ChildItem $s -Recurse -File | Measure-Object Length -Sum).Sum / 1GB)
   ```

3. **Back up the sessions directory before step 8.** Step 8 deliberately deletes
   recordings.

4. In FH6: Settings → HUD and Gameplay → Data Out `ON`, IP `127.0.0.1`,
   Port `5300`, packet format `Car Dash`.

### Step 1 — recovery of the existing crashed sessions

Launch RaceLab. Open **Sessions**.

- The 13 interrupted sessions must each show a recovered frame count in their row
  status (for example `28,505 frames recovered`), not `0`.
- The recovery footnote must appear under Recent sessions while scanning, then
  report the number checked and frames recovered.
- Open one interrupted session. Its banner must say RaceLab did not finish the
  recording *and* state how many frames were recovered. It must **not** show a
  session summary.
- Confirm the app remained responsive during scanning. Launch must not stall.

### Step 2 — storage status

Still in **Sessions**:

- The Recorder footnote must state usage and the limit, e.g.
  `1.5 GB used of 8.0 GB limit`.
- The Recent sessions footnote must state usage, session count, and — since the
  corpus is under budget — must **not** claim anything was deleted.

### Step 3 — normal automatic recording

Start FH6 and drive freely for about three minutes.

- The listener must come up on its own. There must be no Start Listener or Start
  Recording control anywhere.
- Overview must show live telemetry; Recorder must show `Recording`, a rising
  frame count, and `Queued frames` well below 4,096.
- `Recorder drops` must stay at `0`.

Return to the menu and wait for the grace period to expire.

- The session must appear at the top of Recent sessions as `Completed`, with a
  summary.

### Step 4 — automatic analysis and its states

Open the session just recorded, promptly.

- The analysis banner must read `Waiting to be analyzed` or
  `Analysis in progress` — not `Not analyzed`. If a wait is shown it must be a
  plausible number of seconds.
- Reopen after a few seconds. It must read `Analysis available` and render
  events, turn segments, slip episodes and data quality.
- If a queue wait occurred, the job footnote must state `Waited in queue` and
  `Analysis took` as separate figures.

### Step 5 — queue behaviour under several sessions

Drive three short sessions back to back, ending each by returning to the menu.

- Each must complete and appear in the list.
- Opening a later one while an earlier is still being analyzed must show
  `Waiting to be analyzed`, naming the wait.
- All three must eventually reach `Analysis available`.
- No session may ever display `Not analyzed` after having been recorded in this
  run.

### Step 6 — interrupted recording, for real

Start driving. After about a minute, with telemetry flowing, kill the app:

```powershell
Stop-Process -Name RaceLab -Force
```

Relaunch and open Sessions.

- The killed session must appear as `Interrupted · incomplete`.
- It must report a recovered frame count consistent with roughly a minute of
  driving, and its outcome must be `fully recovered` or `N frames recovered`.
- It must have **no summary**.
- Opening it must not error, and the rest of the list must be unaffected.

Repeat once with a **Windows restart** while recording, and confirm the same.

### Step 7 — failed and unsupported analysis, and re-analysis

Pick a completed session with an analysis and corrupt only its analysis
document — never its frames:

```powershell
$d = "$env:LOCALAPPDATA\com.tahagurvardar.racelab\sessions\<session-id>"
Copy-Item "$d\analysis.json" "$d\analysis.json.bak"
'{ "schema_version": 99 }' | Set-Content "$d\analysis.json" -Encoding utf8
```

Restart RaceLab and open that session.

- The banner must read `Unsupported analysis version`, naming both versions, and
  must state that the recording is unaffected.
- A `Re-run analysis` button must appear.
- Press it once. The banner must move to `Analysis available` and the analysis
  must render.
- Confirm `frames.rlframes` and `manifest.json` were not modified (compare sizes
  and timestamps against before).

Then write garbage instead of valid JSON and repeat:

- The banner must read `Analysis failed`, give a reason, and offer the re-run.

Finally confirm the button is **absent** on a healthy session and on one that is
merely `Waiting to be analyzed`.

### Step 8 — retention deletion (destructive; back up first)

With the sessions directory backed up, launch RaceLab with a budget below current
usage:

```powershell
$env:RACELAB_STORAGE_BUDGET_BYTES = 500000000   # 500 MB
```

- Sessions must report deletions: the count of sessions removed and the space
  freed.
- The sessions deleted must be the **oldest by start time**. Verify against the
  list noted in preparation.
- The newest sessions must survive.
- Now drive a new session with the same small budget. The session being recorded
  must **never** be deleted: it must complete normally and appear in the list.
- Open a session immediately after it completes, while it is queued for analysis,
  and confirm it is not deleted out from under the analysis.

Then restore the backup and unset the variable:

```powershell
Remove-Item Env:\RACELAB_STORAGE_BUDGET_BYTES
```

Confirm that with no variable set, the footnote reports the 8 GB default, and
that setting it to `0` reports `no storage limit set` and deletes nothing.

### Step 9 — long session

Drive continuously for **at least 60 minutes**, ideally in one uninterrupted
free-roam session.

- `Recorder drops` must stay `0` throughout.
- `Queued frames` must stay well below 4,096, returning near 0.
- The app must stay responsive and its memory must stay flat — check Task
  Manager at 10-minute intervals; growth proportional to session length is a
  failure.
- On completion the session must analyze successfully, and the analysis duration
  must be seconds, not minutes.
- Expect roughly 0.8 GB on disk for the hour.

### Step 10 — deferred telemetry checks

While driving, open **Diagnostics** and confirm RaceLab still refuses to
interpret what it has not established:

- Raw `boost` and `fuel` are shown as raw values with no unit.
- `best_lap`, `last_lap`, `current_lap` and `distance_traveled` are shown raw.
- The gear **code** is shown, labelled a code. Canonical gear reads `—`.
- Per-wheel channels are listed in packet-offset order, not by corner.

Then confirm the wheel mapping still holds, as in V0.8: brake hard and watch the
front pair compress; accelerate hard and watch the rear pair compress.

### Optional — advance the known limitations

Not required to pass, but each retires a V1.0 blocker:

- **Gear (blocker 3):** drive one car through every forward gear and reverse with
  the in-game gear indicator visible. Record it. Compare the indicator against
  offset 319 frame by frame.
- **Laps (blocker 4):** run a circuit race of at least three laps, so
  `lap_number` increments and `best_lap` / `last_lap` have a chance to become
  non-zero.
- **Boost (blocker 6):** drive a turbocharged car with the boost readout visible
  and compare a held value against offset 284.
- **Slip portability (blocker 2):** record sessions in six to eight different
  cars spanning drivetrains and power, then re-run:

  ```powershell
  cargo run --release --manifest-path src-tauri/Cargo.toml --example slip_portability -- "$env:LOCALAPPDATA\com.tahagurvardar.racelab\sessions"
  ```

### Passing

Steps 1–10 all matched. The version was bumped to `0.10.0` in `package.json`,
`src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json` and
the sidebar badge in `src/components/AppShell.tsx`, and the observed figures are
recorded in section 3a.

Note for future releases: bumping the crate version also changes
`created_by_racelab_version`, `analyzed_by_racelab_version` and
`recovered_by_racelab_version` in newly written files, because all three read
`env!("CARGO_PKG_VERSION")`. Existing files are never rewritten, so a manifest
written by 0.9.0 keeps saying `0.9.0` — which is the point of recording it.
