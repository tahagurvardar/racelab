# V0.7 — Full telemetry dashboard

V0.7 turns RaceLab's engineering screen into a product dashboard. It is a
**frontend-only** release: `src-tauri/` is byte-identical to `v0.6.0`, including
every frozen transport, capture and recorder file, and no Tauri command was
added, removed or changed.

## Product flow

```
RaceLab starts
  -> binds UDP 20440 automatically (V0.2.2 ingress, unchanged)
  -> Waiting for game
  -> FH6 detected (V0.5 protocol lock, unchanged)
  -> Connected
  -> active telemetry starts a session (V0.5.1 lifecycle, unchanged)
  -> live canonical telemetry appears across the dashboard views
  -> the V0.6 recorder records silently in the background
  -> completed sessions remain in Sessions
  -> all protocol/transport/adapter detail lives in Diagnostics
```

## Information architecture

A persistent sidebar shell with two separated groups.

| Group | Views |
|---|---|
| Telemetry | Overview, Engine, Dynamics, Tires, Suspension, Inputs, Race, Sessions |
| Engineering | Diagnostics |

Navigation is a `ViewId` in component state (`src/views/navigation.ts`). No
routing dependency was added: a nine-section desktop window has no address bar,
so a router would add history semantics the product does not have.

A persistent status bar above every view reports the product name, detected
game, connection, health, session state, recording state, vehicle ID and session
duration. Every state carries **text and a glyph** as well as a colour tone;
nothing is communicated by colour alone.

## The canonical-only rule

Product views consume `TelemetryFrame` and nothing else. They never read
`sourceSpecific`, packet offsets, raw input bytes or the raw gear code.

This boundary is mechanical, not a convention:

- `src/telemetry/telemetry-view-model.ts` builds every product view model and
  does not access `sourceSpecific`.
- `src/telemetry/diagnostics-view-model.ts` is the **only** module that reads
  it, and is imported only by `DiagnosticsView`.
- `tests/dashboard-architecture.test.mjs` fails the build if either statement
  stops being true.

An unavailable value renders as `—`. A measured zero renders as `0`. The two are
never conflated in either direction.

## What canonical telemetry actually contains

This is the central constraint of V0.7, and the reason several views are
deliberately sparse.

`telemetry::TelemetryFrame` carries: `active`, `game`, `vehicle_id`,
`game_timestamp_ms`, `engine{rpm, idle_rpm, max_rpm}`, `acceleration`,
`velocity`, `angular_velocity`, `orientation`, `position`, `speed_mps`,
`controls{throttle, brake, clutch, handbrake, steering}`, `gear` and the
adapter-owned `sourceSpecific` envelope.

It does **not** carry power, torque, boost, fuel, tire temperatures, per-wheel
slip or rotation, suspension travel, lap number, race position, lap times, race
time or distance.

| Requested channel | Status | Why it is not a product value |
|---|---|---|
| Power, torque, boost, fuel | Decoded by the FH6 adapter, not canonical | Units unverified ([FH6-PROTOCOL.md](FH6-PROTOCOL.md), "Remaining uncertainties") |
| Tire temperatures | Decoded by the FH6 adapter, not canonical | Unit **and wheel order** unverified |
| Slip ratio/angle, combined slip, wheel rotation, rumble strip, puddle, surface rumble | **Not decoded at all** | They fall in the deliberately opaque byte region 68..211 |
| Suspension travel (normalized and metres) | **Not decoded at all** | Same opaque region |
| Lap number, race position, lap/race times, distance | Decoded by the FH6 adapter, not canonical | Units and sentinel conventions unverified |
| Car class, performance index, drivetrain, cylinders | Decoded by the FH6 adapter, not canonical | Opaque codes with no established enum mapping |
| Gear | Canonical field exists, FH6 supplies `null` | Gear code semantics unestablished, especially the observed `0` and `11` |

Promoting any of these would mean asserting a unit, a wheel order or an enum the
project has not verified, and would change the persisted `TelemetryFrame` schema
that V0.6 sessions are recorded with. Both are out of scope for a frontend
release. Every one of these values remains visible in **Diagnostics** as a raw
adapter number carrying an explicit caveat.

The affected views still render their **complete final structure** — the
four-corner tire and suspension layouts, the engine output cards, the race
timing cards — filled with `—` and a stated reason. When the corresponding
canonical fields land, those views light up with no further UI work.

## View-model and conversion rules

`src/telemetry/formatting.ts` owns every conversion. No component converts.

| Conversion | Rule | Notes |
|---|---|---|
| Speed | `km/h = m/s × 3.6` | Canonical stays m/s |
| Acceleration in g | `g = m/s² ÷ 9.80665` | Presentation only; canonical stays m/s²; axes keep X/Y/Z names |
| Orientation | `° = rad × 180 ÷ π` | Canonical `orientation` is documented x = yaw, y = pitch, z = roll |
| Inputs | `% = normalized × 100` | Sign preserved: steering reads `-38`, not `38` |
| Input bar fill | `min(100, abs(normalized) × 100)` | Magnitude only; an unavailable input draws **no** bar |
| RPM range bar | `(rpm − idle) ÷ (max − idle)`, clamped 0..100 | Returns `null` — and draws nothing — unless both limits exist |
| Lap time | `m:ss.mmm` | Negative input is not a lap time and stays `—` |
| Elapsed | `h:mm:ss` / `m:ss` | Wall duration, not lap timing |
| Counted quantity | Locale digit grouping | e.g. packet counts |
| Identifier or code | **No** grouping | A port, ordinal or opaque code has no magnitude |

**There is no watt-to-kilowatt conversion.** Canonical telemetry has no power
field, and the FH6 power unit is unverified, so applying `W -> kW` to it would
assert a unit the project has not established. A test asserts the helper does
not exist, so it cannot be reintroduced silently.

## Canonical fields used per view

| View | Canonical fields consumed |
|---|---|
| Overview | `speed_mps`, `engine.rpm`, `engine.idle_rpm`, `engine.max_rpm`, `controls.throttle/brake/steering`, `gear`, `vehicle_id`, `game` |
| Engine | `engine.rpm`, `engine.idle_rpm`, `engine.max_rpm` |
| Dynamics | `speed_mps`, `acceleration`, `velocity`, `angular_velocity`, `orientation`, `position` |
| Tires | none available (structure only) |
| Suspension | none available (structure only) |
| Inputs | `controls.throttle/brake/clutch/handbrake/steering` |
| Race | `game_timestamp_ms`; all lap/race fields unavailable |
| Sessions | none — V0.6 manifest and summary metadata only |
| Diagnostics | `sourceSpecific.fh6`, `LiveSnapshot` counters, `StatsSnapshot` |

Canonical fields intentionally not surfaced as product values: `game_timestamp_ms`
appears only as a Diagnostics counter and a Race "Game clock", because it is an
ordering clock rather than a driving measurement; `gear` renders `—` for FH6 by
design.

## Stale and disconnected behaviour

`resolveLiveFrame(snapshot, listenerRunning)` decides, once, whether any live
value may be shown. Views receive the result and cannot bypass it.

| Condition | Availability | Shown |
|---|---|---|
| Listener stopped | `stopped` | "Listener stopped" + how to start it |
| No snapshot yet | `waiting` | "Connecting to the RaceLab backend…" |
| `LISTENING` / `PROBING` / `DISCONNECTED` | `waiting` | "Waiting for game" |
| `CONNECTED_IDLE` / `SESSION_ACTIVE` with no active frame | `idle` | "Connected · not driving" |
| `GRACE` | `grace` | "Telemetry paused · session held" |
| `DEGRADED` | `stale` | "Telemetry degraded" |
| `ERROR` | `stopped` | The transport error |
| Active frame, not stale | `live` | Live values |

The backend already withholds `frame` when telemetry is stale, so a stale
reading cannot reach the UI; `resolveLiveFrame` adds the listener-stopped case
and classifies the reason so each view can state it. **No view ever keeps the
previous reading on screen.**

## Live update architecture

- **Two** polling loops exist in the whole frontend, both started by hooks in
  the app shell, above the view switch: `useLiveTelemetry` (20 Hz) and
  `useRecorderStatus` (2 Hz). Changing views neither starts a second loop nor
  tears the existing one down.
- Backend FH6 input is ~60-75 Hz. The UI reads one **latest** snapshot at a
  time via `startLatestPolling`, which schedules the next read only after the
  previous one settles and floors the interval at 50 ms. A slow IPC read cannot
  build a backlog, and no caller can exceed 20 Hz.
- No frontend module accumulates telemetry. There is no history array, no frame
  queue and no chart buffer; a test asserts nothing pushes a frame or snapshot
  into a collection.
- V0.2.2 transport counters still arrive as 4 Hz backend **events**, unchanged.
  V0.3 capture statistics still arrive as 4 Hz events inside `CapturePanel`.
- The Sessions view polls nothing. It receives recorder status as a prop and
  re-reads the manifest listing only when `completed_sessions` changes, so
  opening Sessions cannot affect telemetry ingestion.
- Every effect returns its disposer; the poller's own disposer is returned
  directly from `useEffect`, and event listeners unlisten with a disposal guard.

## V0.6 behaviour preserved

Sessions is a restyled move, not a rewrite. It still calls only
`list_recent_sessions` and `get_session`, still reads manifest and summary
metadata alone, never requests `frames.rlframes`, and still exposes no recording
control. Completed / Interrupted classification, data quality, recorder drops
and every summary metric render exactly as in V0.6. The persistence format is
untouched.

## Visual direction

Dark, dense and restrained: a near-black base with two lifted panel levels,
tabular-figure monospace for every reading so digits do not jitter at 20 Hz, and
a strict hierarchy of hero value → metric card → diagnostic row. Unavailable
cards use a dashed border and muted type rather than a colour swap. All colour,
spacing, radius and typography live as CSS custom properties on `:root`. No
gradient washes, no glassmorphism, no animated transitions, no charts. The
layout collapses the sidebar into a horizontal nav under 900 px and to a
single-column metric grid under 720 px.

## Out of scope, and still out of scope

No driving coach, AI engineer, tuning advice, understeer/oversteer judgement,
corner detection, track map, replay, session graphs, lap comparison, heatmaps,
car-name database, gear semantic resolver, additional game adapter, cloud sync,
accounts, retention policy or delete-session UI. No value is labelled good, bad,
overheating or excessive.
